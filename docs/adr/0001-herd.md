# ADR 0001: herd — a Substrate-API-compatible microVM actor runtime

- Status: accepted for R0 (issue PLT-112, program PLT-111)
- Date: 2026-10-30
- Spec: Everdict workspace `docs/specs/architecture/herd.md` rev 2 (with the rev 3 owner decision R-D10), which amends
  `herder-everywhere.md` (PLT-101)

## Context

Everdict needs an actor layer — checkpoint/restore, a warm pool keyed by template, resume-on-request ingress, a
per-actor egress gateway with credential injection — on hosts that have no Kubernetes. Nomad has none of it, and
Everdict rebuilt pieces of each inside its control plane. Substrate has all of it, but only on Kubernetes. Substrate's
useful core is its API and lifecycle model (`api/ateapi/v1/ateapi.proto` at commit `6d7b3f49`) and the in-actor guest
API of `agent-substrate/env`; its microVM class is Kata + Cloud Hypervisor with containers' rootfs as a host overlay,
DurableDir volumes over one virtio-fs share, and memory snapshots.

No single VMM gives memory snapshots on both macOS and Ubuntu, so herd uses one per platform and makes each host
declare what it can do.

## Decisions taken from the spec

### R-D1 Build our own, as a separate product

**Decision.** herd is built as a separate product in its own repository, `github.com/everdict/herd`, usable without
Everdict. It runs on a Nomad cluster and on hosts with no cluster tool (one host, or several hosts that only share a
network path to herd-api).

### R-D2 Speak Substrate's API

**Decision.** herd-api implements a pinned subset of Substrate's `Control` service plus a capability extension
(`herd.ext.v1.Capabilities`). Everdict keeps one runtime integration — the Substrate API — for real Substrate and for
herd, and one conformance suite runs against both. The subset and its pin are A-4; the extension is A-5.

### R-D3 Components

**Decision.** herd has the roles Substrate has, as five components: `herd-api` (records, scheduler, suspend/resume
workflows, snapshot store, authn/authz), `herdlet` (the node agent; it dials out, no inbound port), `herd-router`
(resume-on-request ingress over node tunnels), `herd-egress` (default-deny egress, hostname rules, credential
injection) and `herd-guest` (the in-VM agent).

### R-D4 Deployment modes

**Decision.** Three deployment modes on one code path: all-in-one (one host, SQLite), multi-host join with no cluster
tool (`herdlet join`), and Nomad (herd-api as a service job, herdlet as a system job; Nomad supervises the processes,
herd places the actors).

### R-D5 Language

**Decision.** herd is written in Go (module `github.com/everdict/herd`, A-2).

### R-D6 Everdict's laws carry over

**Decision.** Everdict's laws hold in herd: a delete is answered gone, present or unknown, and unknown is never folded
into absent; state is durable before release (a snapshot is not reported until it is complete, and an actor's VM is
not released before its snapshot is); no credential in the actor (herd-egress injects credentials outside the VM).
In R0 the `vmm` interface already answers presence in three values and its contract suite checks that a timed-out or
unanswered call is unknown, never gone (A-6).

### R-D7 Every actor is a Linux microVM

**Decision.** Every herd actor is a Linux microVM, in all three deployment modes. Inside it, the actor's ActorTemplate
defines containers (OCI images run by crun under herd-guest) and volumes (DurableDir subdirectories of one virtio-fs
share), as in Substrate's microVM class. There are no docker, runsc or Seatbelt backends in herd. A host without KVM
(Ubuntu) or Virtualization.framework (macOS, Apple Silicon) cannot join, and `herdlet doctor` says why.

### R-D8 One guest, two hypervisors

**Decision.**
- Ubuntu (x86_64, arm64): Cloud Hypervisor (pinned, v54.0) + virtiofsd (>= 1.11); rootfs from read-only erofs/ext4
  images built from OCI layers plus a writable layer; network = TAP into herd-egress (nftables default-deny + proxy);
  control over hybrid vsock.
- macOS hosts (Apple Silicon, macOS 14+; 26+ for vmnet custom networks): Virtualization.framework via Code-Hex/vz; the
  same Linux guest kernel (arm64) and herd-guest; virtio-fs volumes; network = file-handle attachment into
  herd-egress's userspace stack (gvisor-tap-vsock); native vsock.
- The same guest kernel configuration, initramfs and herd-guest build for both architectures, arm64 and amd64 (A-7).
  A vsock transport adapter hides hybrid vs native vsock.

### R-D9 Capabilities are declared, not assumed

**Decision.** Each host declares `suspendMaxFidelity` and `restoreFamily` (in `vmm.Capabilities` and in
`herd.ext.v1.WorkerCapabilities`); the scheduler never assumes them.

| | Ubuntu (Cloud Hypervisor) | macOS host (Virtualization.framework) |
|---|---|---|
| suspendMaxFidelity | MEMORY (eager restore with virtio-fs) | VOLUMES (stop containers, keep volumes); MEMORY only if the host shows it can save machine state in its session — declared per host |
| restore elsewhere | within the same restore family = (CH version, arch, CPU feature class); otherwise VOLUMES | never at MEMORY (the save file is bound to one Mac and user); VOLUMES anywhere |
| restoreFamily | `microvm-ch-<arch>-<cpu-class>` | `microvm-vz-arm64-<host>` (memory) |
| portable family | `microvm-volumes` | `microvm-volumes` |
| egress | TAP + nftables + proxy | file-handle + userspace stack |

Moves between a Mac and an Ubuntu host always go through VOLUMES: the volume tree, image references and the container
spec; images are published multi-arch (amd64 + arm64). The R0 spikes confirm this table; see "R0 spike results".

### R-D10 Linux guests only; macOS stays as it is

**Decision.** herd runs Linux guests only and builds no macOS guest class. macOS-native delegation keeps Everdict's
current Seatbelt lane (Nomad raw_exec + Seatbelt + pf; PLT-89/90) unchanged: it is not moved into herd, and it is
excluded from the direct-mode retirement (PLT-110).

## Decisions this ADR makes

### A-1 Name

**Decision.** The product is `herd`; the components keep the spec's names (`herd-api`, `herdlet`, `herd-router`,
`herd-egress`, `herd-guest`). The repository is `everdict/herd`. Its visibility is not decided here: it is the
owner's call on PLT-111.

### A-2 Module and toolchain

**Decision.** The Go module is `github.com/everdict/herd` with `go 1.25`. Library code returns errors and does not
panic.

### A-3 License

**Decision.** herd is licensed under the Apache License 2.0 (the `LICENSE` already in the repository). It matches the
license of the Substrate API definition herd vendors, whose copyright and license notice are kept in the vendored file
and in `NOTICE`.

### A-4 The pinned Substrate API subset

**Decision.** herd pins Substrate's `api/ateapi/v1/ateapi.proto` at commit
`6d7b3f49f6154d52a1de46c94a1481868a5ed042` (sha256 in `api/ateapi/v1/UPSTREAM.md`) and serves these `Control` methods:
CreateActor, GetActor, ListActors, UpdateActor, DeleteActor, SuspendActor, ResumeActor; CreateTag, GetTag, ListTags
(DEFAUL-1613, A-41), DeleteTag;
CreateActorTemplate, GetActorTemplate, ListActorTemplates (DEFAUL-1613, A-41), DeleteActorTemplate; GetActorEgressPolicy,
CreateActorEgressPolicy, UpdateActorEgressPolicy, DeleteActorEgressPolicy; ListWorkers (PLT-219).
- The subset is cut mechanically by `internal/cmd/protosubset` from a byte-for-byte copy of the upstream file: the
  listed methods, every message and enum they reach, and the `resource`/`method` annotations. A test regenerates it
  and fails on any hand edit; another fails when a listed method is missing or an unlisted one appears.
- (PLT-330, A-34) herd's own fields on upstream messages are appended by the same cut from
  `api/ateapi/v1/herd-additions.txt`, each marked "herd addition" and numbered from 1000: today only
  `CreateActorTemplateRequest.image_pull_auth`.
- The protobuf package stays `substrate.ateapi.v1`, so full method names are wire-identical to Substrate's; only
  `go_package` changes. Consequence: one Go binary cannot link both Substrate's and herd's generated package (they
  register the same names). Everdict's integration is not Go, so this does not bite it.
- R0 generates message types only (protoc-gen-go v1.36.12, runtime google.golang.org/protobuf v1.36.12 — Substrate's
  own pin). The gRPC service stubs and the grpc dependency arrive with herd-api in R1.
- (PLT-219) ListWorkers answers Substrate's `Worker` for each worker record herd-api keeps (what a herdlet declared at
  registration, A-5), by name and paged like ListActors. Everdict's herder reads the workers' sandbox classes from it.
  `metadata` is the record's (global: no atespace; uid, version, times); `labels` are the herdlet's; `status.state`
  is ACTIVE while the herdlet's link to this herd-api is up and UNAVAILABLE otherwise; `status.capacity.actors` is
  its slots and `status.allocated.actors` the actors herd-api holds on it (herd places by slots, so CPU and memory
  are not reported). `status.sandbox_classes` has one entry, `microvm`, whose `default_runtime.version` carries what
  Substrate's message has no field for: `schema_version: herd-v1` with the attributes `architecture`, `platform`
  (`linux-cloud-hypervisor` or `darwin-vz`), `suspend_max_fidelity` (a `SnapshotFidelity` name, e.g.
  `SNAPSHOT_FIDELITY_MEMORY`), `restore_family`, `portable_restore_family` and `hypervisor_version`, sorted by key,
  an empty one left out. The Kubernetes coordinates (`worker_namespace`, `worker_pool`, `worker_pod`, ...) and the
  epochs are empty: herd has neither. Workers are global, so the caller must be one the Authorizer lets read in
  some atespace it names; a herdlet or join credential may not list them. `herd-api workers` and the Capabilities
  extension read the same records.
- Not in the subset: RevertActor, UpdateTag, the other worker methods (GetWorker,
  CreateWorker, DrainWorker, ...), atespaces, access policies, credential minting and the WorkerService. Adding one is a change to `subset.txt` and this ADR.

### A-5 The capability extension

**Decision.** herd's extension is the service `herd.ext.v1.Capabilities` (GetWorkerCapabilities,
ListWorkerCapabilities) returning `WorkerCapabilities`: worker, platform (Cloud Hypervisor or VZ), arch,
`suspend_max_fidelity` as Substrate's own `SnapshotFidelity`, `restore_family`, `portable_restore_family`,
`hypervisor_version`, and the `reason` a host declares less than its platform could.

### A-6 The hypervisor boundary

**Decision.** herdlet reaches a hypervisor only through `vmm.VMM`: Capabilities, Boot, Snapshot (VOLUMES or MEMORY),
Restore, Inspect, Delete.
- Presence is three-valued (gone, present, unknown). Delete answers gone only after verifying it; a VM that survives
  is present with `ErrDeleteNotVerified`; a call that times out or gets no answer is unknown with the reason.
- A snapshot that did not complete is not returned. A MEMORY snapshot restores only in its restore family
  (`ErrRestoreFamilyMismatch` otherwise); a VOLUMES snapshot restores anywhere.
- `vmm/vmmtest` is the contract. The in-memory fake (`vmm/fake`, with injected hangs, unreachable answers and a delete
  the hypervisor does not carry out) runs it in every `go test`; the Cloud Hypervisor and VZ backends must run it on
  real hosts.
- The backends sit behind build tags: `vmm/cloudhypervisor` (linux) and `vmm/vz` (darwin). In R0 they are stubs that
  answer a typed `*vmm.NotImplementedError` and presence unknown; R2 (PLT-114) implements them.
- (R2b, PLT-182) `vmm/vz`'s logic builds on every platform against its own hardware interface (`vz.Hypervisor`);
  only the Code-Hex/vz binding (`vz.Native`) sits behind `darwin && arm64 && cgo`, and `vmm/vz/vzfake` runs the
  contract and the backend's own tests in every `go test`. A Mac declares MEMORY only when validateSaveRestoreSupport
  and a real save/restore round trip both succeeded on it.
- `vmm.Fidelity` uses Substrate's `SnapshotFidelity` numbers (VOLUMES = 1, MEMORY = 3).

### A-7 One guest build for both architectures

**Decision.** The guest kernel is built from Cloud Hypervisor's kernel tree at `ch-release-v7.2.8-20261009` (commit
`639d0886248cd90799b0b590f7a62a1a3565a815`), the release the R0 spikes booted on both hypervisors. One shared
configuration fragment (`guest/kernel/herd-guest.config`) is merged onto `allnoconfig` together with a small
architecture fragment that may set only what cannot be shared (console, interrupt controller, PCI host, paravirt);
a test enforces that. `guest/build.sh` fails if kconfig drops a requested symbol. One initramfs list serves both;
herd-guest is `/init`. The output is `bzImage` for amd64 (Cloud Hypervisor) and `Image` for arm64 (Cloud Hypervisor
and Virtualization.framework).

### A-8 Restore family names

**Decision.** `microvm-ch-<arch>-<cpu-class>` with `arch` in {amd64, arm64} and a lower-case CPU feature class label;
`microvm-vz-arm64-<host>` with a lower-case host label; `microvm-volumes` for every VOLUMES snapshot. Hosts that
declare the same CPU class must be able to restore each other's memory snapshots; choosing the class (e.g. the CPUID
leaves Cloud Hypervisor checks) belongs to the Cloud Hypervisor backend in R2.

### A-9 Dependencies

**Decision.** R0 depends on google.golang.org/protobuf only. Hardware libraries (Cloud Hypervisor's API client,
Code-Hex/vz with cgo) enter only inside their backend packages, behind their build tags.

### A-10 herd-guest (R5, PLT-104)

**Decision.** `cmd/herd-guest` is `/init` of the guest and the agent inside it.
- **API.** It serves agent-substrate/env's `ateenv.v1alpha` ProcessService and FileSystemService, wire-compatible: the
  proto is vendored byte for byte from env at commit `281e86085bb0b6d3090ff3fa82d722cf0d9f2f0b`
  (`api/ateenv/v1alpha/UPSTREAM.md`), and a test compares herd's generated descriptor with the one env's own
  generated code embeds. env has no stat or list; herd adds them as `herd.ext.v1.FileInfoService` (StatFile,
  ListDirectory), so an env-only client is unaffected. The target container is chosen by the request metadata key
  `x-herd-container` (default: the first container of the template).
- **gRPC.** First served by `internal/grpcwire` (gRPC framing over the standard library's unencrypted HTTP/2) while
  grpc-go was not vendored; now grpc-go (A-12), with no wire change. `test/interop` (a separate module) checks the
  guest against grpc-go with env's own generated client.
- **Transport.** The guest listens on AF_VSOCK (the same in the guest under Cloud Hypervisor and
  Virtualization.framework) or a unix socket (tests, `serve -local`). The host side of Cloud Hypervisor's hybrid vsock
  (unix socket + `CONNECT <port>`) is `transport.DialHybridVsock`; VZ's native vsock dialer belongs to R2.
- **Detached exec.** Every process is Everdict's record `/everdict/exec/<id>/{cmd.sh,pgid,out,err,exit,in}` inside the
  target container (herd adds `meta.json`, the start request, and `in.closed`). herd-guest is bound read-only into each
  container at `/.herd/herd-guest`; `crun exec --detach` starts `herd-guest shim <dir>` there, which runs
  `/bin/sh cmd.sh` as a new session, appends stdout/stderr straight to `out`/`err`, writes `pgid` and then `exit`
  (code, or 128 + signal). `in` is a FIFO the shim reopens after each writer, so a guest restart is not end of input;
  stdin ends only when `in.closed` exists. The service keeps no process table: every call reads the record, so a
  restarted guest follows a running exec from the client's byte offsets and reports its exit. Signals go through
  `herd-guest signal <pgid> <sig>` exec'd in the container (pids are the container's). Timeouts are re-armed from
  `meta.json` after a restart.
- **Boot.** As PID 1: pseudo filesystems, then the virtio-fs share (tag `herd`) at `/mnt/volumes`, then the plan
  herdlet wrote at `.herd/actor.json` in the share, then every DurableDir volume as a directory `<share>/<name>`
  (a DNS label; an existing non-directory there, e.g. a symlink, is refused), and only then each container: image
  block device (erofs or ext4) read-only, an overlay on tmpfs on top, `config.json` from `guest/oci` with the volumes
  as bind mounts whose sources must lie inside the share, and `crun run --detach`. The container's process is
  `herd-guest cinit -- <argv>`, which reaps the shims reparented to it. `oci.Runtime` and `initd.Mounter` are the
  hardware boundaries; tests run them as fakes.

## Decisions for R1 (herd-api, PLT-113)

### A-11 Records and the all-in-one store

**Decision.** Actors, actor templates, tags, egress policies, workers and spaces are records in `store.Store`. The
store assigns uid and version; every update and delete names the uid+version it was read at, and a stale one is refused
(Aborted on the API); updates through the API must carry both. Implementations: `memstore` (in memory) and
`boltstore` (the all-in-one mode), both held to the `storetest` contract, which includes durability across a reopen. This replaces
the SQLite that R-D4 names for the all-in-one mode.
- **Why bbolt.** go.etcd.io/bbolt is pure Go (no cgo, so one static herd-api for amd64 and arm64), a single file,
  and its write transactions are serialized and fsynced on commit, so a precondition checked inside the transaction
  holds against every other writer of the file. A pure-Go SQLite (modernc.org/sqlite) vendors to about 144 MB for
  what herd-api needs from it — get, compare-and-swap, list by prefix — and cgo SQLite breaks the static build.
- **Not the multi-host store.** bbolt holds an exclusive file lock: one herd-api process per file. Several herd-api
  replicas (multi-host join and Nomad with more than one herd-api) need a shared store; that is Postgres, behind the
  same interface and contract, later.

### A-12 gRPC is grpc-go

**Decision.** herd-api (`substrate.ateapi.v1.Control`, `herd.ext.v1.Capabilities`, the herdlet link) and herd-guest
(`ateenv.v1alpha` ProcessService and FileSystemService, `herd.ext.v1.FileInfoService`) serve on grpc-go v1.83.2.
`internal/grpcwire`, the standard-library stand-in both used before grpc-go was vendored, is removed; this supersedes
A-10's "No grpc-go" bullet and changes no wire byte (same full method names, same protobuf messages). The service
descriptors are hand-written (`apiserver/service.go`, `guest/agent/service.go`) because protoc-gen-go-grpc is not
available where herd is built; each is checked against the proto's own service descriptor by a test, so a method
added to the proto without a handler fails. herd-api serves cleartext HTTP/2; until it terminates TLS itself, TLS is
terminated in front of it, since bearer tokens travel in the request metadata.

### A-13 The herdlet link

**Decision.** A herdlet dials herd-api and opens one bidirectional stream, `/herd.ext.v1.Herdlet/Link` (package
`link`); herd-api never dials a herdlet, and a test keeps dialers out of `apiserver`, `link` and `cmd/herd-api`. The
herdlet registers its worker name, class, labels, declared capabilities and capacity (slots, warm VMs per template);
herd-api sends work (boot, snapshot, restore, delete, inspect) and the herdlet answers each with a three-valued outcome:
done, failed (definitely not done) or unknown. No answer before the deadline, a broken link or a herdlet that is not
connected are unknown. A delete is done only with the VM verified gone. A herdlet credential registers only the worker
it names. Messages are JSON (gRPC content-subtype `json`) until the link gets a `.proto`.

### A-14 Workflows, durability and owed steps

**Decision.** SuspendActor (synchronous unless DURABILITY_MODE_ASYNCHRONOUS) snapshots at the template's preferred
fidelity capped by the worker's declared `suspend_max_fidelity`, verifies the object in the snapshot store against the
digest the herdlet answered, records key+digest in the actor record, and only then asks the herdlet to release the
VM. A step whose outcome is unknown stays owed on the actor (SUSPENDING, RESUMING or DELETING; the reason in the
`herd-owed` response trailer and the call's Unavailable status) and `Reconcile` retries it; DeleteActor removes the
record only after a verified gone and verified deletion of its snapshot objects. Fork is CreateTag{source_actor} (a
tag owns a copy of the snapshot) + CreateActor{actor_template, source_tag}.

### A-15 Scheduling, snapshot store and authentication

**Decision.** The scheduler places an actor only on a connected herdlet of its class with a free slot (slots stay
taken until a release is verified), matching labels, and for a MEMORY snapshot the same restore family; VOLUMES
restores anywhere; a warm VM of the template is preferred; otherwise it refuses with a typed reason per worker
(ResourceExhausted). The snapshot store is `snapstore.Store` with a local-disk implementation (fsync + rename, sha256
digest) and an S3 one (`snapstore/s3`, A-25); both run one contract suite (`snapstore/storetest`). Authentication and per-space authorization are interfaces; this
round implements them with one static HS256 key (`auth.StaticKey`, roles read/write per atespace, a separate herdlet
credential).

## Decisions for R3 (herd-router and the herdlet tunnel, PLT-115)

### A-16 The tunnel: the herdlet dials the router

**Decision.** A herdlet dials herd-router as it dials herd-api and holds one control stream,
`/herd.ext.v1.Tunnel/Control` (package `tunnel`, JSON like the link). For each connection the router needs it sends
Open{id, vm, port}; the herdlet connects to the guest through its `herdlet.GuestDialer` (Cloud Hypervisor: hybrid
vsock, `cloudhypervisor.VMM.DialGuest`; VZ: native vsock, R2; tests: `vmm/fakeguest`) and opens a new outbound stream,
`/herd.ext.v1.Tunnel/Data` with `herd-tunnel-id`, carrying that connection's bytes in a small binary frame codec
(`application/grpc+herdframe`) — or answers Refused{reason}. No node has an inbound port; a test keeps dialers out of
`router`, `tunnel` and `cmd/herd-router` (whose one gRPC client is herd-api). Only a herdlet credential opens a
tunnel, only for the worker it names, and a data stream is paired only with an Open sent to that worker.
- `link.Work` names its `Cause` (suspend or delete). On a snapshot for suspend and on a release, the herdlet cuts the
  VM's streams with a typed reason (`actor-suspended`, `actor-deleted`) sent before the stream's end, and refuses new
  ones until the VM is booted or restored again; a snapshot that failed reopens it. Cutting at the snapshot keeps a
  client from reading output a MEMORY snapshot does not contain.

### A-17 herd-router

**Decision.** `cmd/herd-router` serves clients over HTTP/1.1 and prior-knowledge h2c and herdlets' tunnels over gRPC.
- **Naming and authn.** `ate-target-actor: <atespace>/<actor>`, Substrate's header and format. The bearer JWT is
  verified (the same `auth.Authenticator` as herd-api) and must grant write in that atespace — routing reaches exec and
  files — before anything is resumed or dialed; herdlet credentials are refused. herd-api calls carry the client's own
  token, so herd-api authorizes the resume too. The token is not forwarded to the guest.
- **Ports.** Ordinary requests go to the guest's API port (herd-guest, vsock 8080; `-default-port`) as h2c; Substrate's
  default is the actor's port 80. `CONNECT host:port` reaches another port as a byte tunnel resolved (and resumed)
  when the CONNECT arrives; unlike Substrate, the requests inside a CONNECT are not re-routed one by one.
- **Parking.** A request to an actor that is not RUNNING is parked: a SUSPENDED actor gets one ResumeActor shared by
  every parked request (on its own context, so a client that leaves does not abandon it), and the request is delivered
  once herd-api answers RUNNING and the worker's tunnel opens. Past the parking budget (`-parking-budget`, 30 s) the
  answer is a typed 503: HTTP 503 with `herd-reason: parking-budget-exceeded` and, for gRPC, grpc-status UNAVAILABLE in
  the same trailers-only response. If the actor's last known worker holds no tunnel to the router when the budget
  ends, the reason is `node-unreachable` instead, whether or not herd-api answered inside the budget (its error is
  added as detail). NotFound, DELETING and authorization failures are answered at once.
- **Long streams.** The budget bounds only the wait. A delivered request runs on the client's own context, the HTTP
  server has no read, write or idle timeout (only the header read is bounded), and gRPC streams have none. A cut stream
  ends with the reason in the `herd-reason` trailer (grpc-status UNAVAILABLE); the client re-attaches by exec id and
  offsets, and that request resumes the actor. An HTTP/1.1 CONNECT has nowhere to put a reason and is closed.
- **Behind NAT.** Herdlets keep their tunnel alive with gRPC keepalive pings; the router permits them every 10 s.

## Decisions for R4 (herd-egress, PLT-116)

### A-18 herd-egress: one policy model, decided by name, two plumbings

**Decision.** herd-egress (`egress`, `cmd/herd-egress`) enforces Substrate's own `EgressPolicy` — the message pinned
in `api/ateapi/v1` (A-4), not a herd copy: http, https (intercepted) and tls_passthrough rules, hostname patterns,
ports, `replace_headers` from a `credential_uri` or an `actor_jwt`. `egress/policy` compiles it with Substrate's
admission rules (pattern syntax, IP addresses refused as hostnames, no two rules tying on a name and port among the
rules that decide on the same input) and its precedence (exact name over wildcard, then a named port over all
ports); herd-api refuses an invalid policy with InvalidArgument on create and update.
- **Default-deny, host-side first.** No policy, an empty policy and a policy that does not compile all refuse
  everything. Before any rule is consulted, the `Guard` refuses host-side targets: IP literals, loopback, private
  (RFC 1918, ULA), link-local, CGNAT, multicast and reserved ranges, metadata endpoints and names
  (169.254.169.254, fd00:ec2::254, 100.100.100.200, `metadata.google.internal`, `*.internal`, `localhost`), and the
  host's and herd-api's configured addresses and names. Every address a listed name resolves to is checked again
  before the dial; a name with any host-side address is refused.
  The one operator exception is a lab allowance (PLT-207): `-egress-allow-prefix <prefix>` (repeatable, on
  `herd`, `herd-egress` and `herdlet`) opens exactly that prefix inside a default range, so a lab echo host on a
  tailnet can be listed by name; one that is not masked, contains a whole default range or a metadata endpoint, or
  opens nothing is refused at start, the host's own addresses stay refused under it, IP literals stay refused, and
  a set allowance is logged at start, reported in the worker's capabilities and printed in the conformance header.
  It exists for a conformance echo host only (docs/conformance.md); it opens an address to any name that resolves
  there, so it is not how a product service is reached.
- **Declared host services (DEFAUL-1599).** A service on a node's private address (a herder's door relay) is reached
  as a declared host service, not as a network destination: `-host-services-file` (on `herd-egress` and `herd`) names
  a file of lines `<name>:<port> <address>:<port> [loopback]` (blank lines and `#` comments allowed), re-read every
  `-interval`. A flow to exactly a declared name and port is still decided by the actor's policy first (a declared
  name with no rule is refused, on the transparent path, an explicit-proxy request, a CONNECT and a ClientHello
  alike); it skips only the Guard's name check (the names live under `herd.internal`) and, allowed, is dialed
  at exactly its target, with no lookup and no address check. Every other destination is unchanged: a public name that
  resolves to the same private address, or the declared name on another port, stays refused host-side. The
  synthetic DNS knows nothing of declarations. At load, a line whose target is a metadata endpoint, an unspecified
  address, a `-host-addr`, the Control (`-api`) or router (`-router`) endpoint, or loopback without the `loopback`
  field is dropped alone with a log; a malformed file changes nothing (at start it refuses the start). On Nomad the
  herd-egress task renders the file from service discovery: each service tagged `herd-host-service` is
  `<service>.herd.internal` on its port at its registered address, and the file is empty when none is, so no address
  is an input of the job. Declared services are logged, not reported in the worker's capabilities (that would need
  a capabilities field; herd-egress is not the process that reports them). A Mac's in-process gateway (A-21) does
  not read the file yet.
- **By name, never by address (Everdict defect PLT-180).** A decision is taken on the TLS ClientHello's SNI, on each
  HTTP request's authority, or on a CONNECT target (whose tunneled SNI or Host must name the same host). The gateway
  dials only the name it decided on, resolving it afresh for each connection; the address the VM connected to is
  never matched or dialed, only its port. A rotating listed host stays reachable; an unlisted host on a listed
  host's address stays refused.
- **Interception and credentials.** A ClientHello decided by an https rule is terminated with a leaf from the
  gateway CA (herdlet installs `CA.CertPEM` in the guest) and every request inside it is decided on its authority;
  TLS is re-originated to that name. The deciding rule's `replace_headers` replace a header the request carries with
  `prefix + credential`, resolved on the host (`Credentials`: `ate-secret://<class>/<name>/<tail>` through
  registered providers; `ActorJWTs`: ES256 JWTs naming the actor, reused while more than half their lifetime
  remains). The actor holds only a placeholder; a request without the header is forwarded without it.
- **Live updates.** Each actor's compiled policy is an atomic pointer read on every decision. The `Syncer` reads
  every bound actor's policy from herd-api's Control API every interval (default 1 s), so an update reaches the
  next request on an actor's open connections; an open passthrough connection keeps its decision until it ends, as
  in Substrate. An unanswered read keeps the last policy (unknown is not absent); NotFound is deny-all. A
  decision never uses a read older than `PolicyLease`, and a refusal reads again (A-32).
- **DNS.** The VM's resolver is herd-egress's `SyntheticDNS`: every A query is answered with one address that routes
  to the gateway, nothing else, and no query leaves the host.
- **Ubuntu plumbing.** `egress/nft` renders, per VM, a TAP and its own nftables table `inet herd_<id>`: anti-spoofing
  and non-IPv4 drop at prerouting (raw), every TCP connection from the VM redirected to herd-egress's transparent
  listener (`SO_ORIGINAL_DST` gives the port) and UDP 53 to its DNS, input from the TAP accepted only for those
  redirected flows, forward and output to the TAP dropped; drops are counted in named counters. The table is loaded
  before the link comes up. The renderer is golden-tested; `TestRealHostEgress` (HERD_EGRESS_REAL=1) applies it in
  network namespaces and measures the refusals. The VM gets a static address on a /30 (or wider) link.
- **macOS plumbing.** The VM's network device is a file-handle attachment into a userspace stack per VM
  (`egress.Stack`, `StackFactory`): TCP flows come out as `Flow`s into the same gateway, DNS to the gateway address is
  answered by `SyntheticDNS`, everything else is dropped. gvisor-tap-vsock behind that interface and the vz
  attachment are A-21 (R7); `egress/stacktest` is the fake the gateway is tested through.
- **Each VM's link (PLT-206).** herdlet (`egress/tapnet`, `deploy.linuxNet`) leases every VM a /30 of `-net-pool`
  (default 10.88.0.0/16; slot i is the TAP `herd<i>`, MAC 02:68:64:<i>, host .1, VM .2), first choice a hash of the
  VM id, kept in `<state>/net/leases.json` so a restarted herdlet gives no slot twice. `machine.Network` is the
  boundary: `Machines` leases before it writes the plan, brings the TAP and table up (`nft.Apply`: table before link
  up) before Boot or Restore, and takes them down after the VM is verified gone; Cloud Hypervisor gets the TAP as
  `vmm.Spec.NIC` (`net: tap, mac`; a MEMORY restore re-opens the TAP its config names, so it is re-created first).
  herd-guest reads `Plan.Network` and, before any container starts, sets the address and the default route via
  the host's address; each container gets `/etc/resolv.conf` naming the host's address (UDP 53 is redirected to
  `SyntheticDNS`) and herd-egress's CA appended to every trust bundle its image has (resolved inside the rootfs,
  read through `os.Root`), plus alone at `/etc/ssl/certs/herd-egress-ca.pem`. herdlet binds each running VM's
  address to its actor in herd-egress's `-bindings` file (written atomically and read back), from the actor herd-api
  names in the work (`OnActor`; again under the snapshot's VM id after a fork's MEMORY restore). A suspend takes the
  TAP, table and binding down and keeps the lease; a delete releases the lease too. Teardown answers gone only
  when ip(8) and nft(8) answer that the TAP and the table do not exist and the binding reads back absent; a TAP
  left behind is present (`ErrDeleteNotVerified`), no answer is unknown. A MEMORY bundle records its link
  (`Manifest.Network`); the restoring host claims exactly that link, and if another VM holds it the actor
  cold-boots on a link of its own, as a second fork of one memory does. herd-egress keeps its generated CA (key
  beside `-ca-out`) so guests booted before a restart still trust it; the all-in-one keeps it in its data directory.
  `TestRealHostTAPEgress` (HERD_TAP_REAL=1, root, KVM) runs the egress walk and the credential header from real
  Cloud Hypervisor guests.
  The path explains itself (PLT-206 round 2, after a real run whose guests could not resolve): herdlet logs each
  lease, up, bind and verified down, checks after every boot and restore that the TAP has a carrier (a TAP no
  hypervisor holds reads NO-CARRIER/DOWN and carries nothing), and warns at start about other tables' input chains
  that drop by policy, since nftables drops what any base chain drops and those chains also see the redirected
  flows; herd-guest logs its interface, address, route, resolver and CA mounts to the console and probes its
  resolver once (`initd.ProbeDNS`); `TestRealHostTAPEgress` first dumps one actor's network from inside its guest
  and from the host.
  Host firewalls (PLT-206 round 3, a real run on an Ubuntu host with ufw and Tailscale): nftables drops a packet
  that any base chain on its hook drops, so an input chain of another table with policy drop (iptables-nft's `ip
  filter INPUT` under ufw or Tailscale, firewalld's) dropped the VMs' redirected DNS whatever herd's table accepted.
  By default (`-host-firewall=insert`) Up inserts, at the top of each such ip or inet chain, the VM's two accepts
  (`nft.HoleRules`: from its TAP to the host's TAP address, herd-egress's TCP and UDP port, comment
  `herd-egress:herd_<id>`) in one nft transaction; ip6 chains get none (VMs speak IPv4 only). The DNAT condition
  stays enforced by herd's own table, which keeps the accepts expressible in iptables-nft. Down deletes them by
  handle, found again by their comment (also after a herdlet restart), and answers gone only when none is left.
  `-host-firewall=refuse` fails Up instead, naming the chains and the iptables/ufw commands that let the flows in.
  iptables-legacy rules are not seen.
- **Guest boot failures and NIC choice (PLT-206 round 3, a real Mac run).** herd-guest configures only an Ethernet
  NIC (sysfs type 1 with a device link; the arm64 kernel's sit0 is not one), and a Mac VM's NIC has a MAC from its VM
  id (`egress.StackMAC`, set by vz and named in the plan), so the guest finds it as on Linux. A boot herd-guest
  cannot finish is written to the share (`initd.BootErrorPath`) and the VM is ended (a restart, which both
  hypervisors answer by ending the VM; vz's default command line also carries panic=-1). The herdlet then fails the
  start at once with `machine.ErrGuestBoot` and the guest's reason, or, where the start answered before the guest
  ran (Cloud Hypervisor), reports it with the VM's exit.
- Not yet: UDP and QUIC (refused, as in Substrate), STARTTLS, IPv6 in the guest, and the credential providers
  beyond a static map and a directory.

## Decisions for R2c (templates into VMs, PLT-183)

### A-19 herdlet turns a template into a VM

**Decision.** `herdlet/machine` turns a template into a microVM on the host's `vmm.VMM`; `cmd/herdlet` runs it with
Cloud Hypervisor (Linux) or Virtualization.framework (macOS, cgo).
- **Templates on the link.** herd-api sends the template with every boot (`link.Work.Spec`, a `link.Template`: the
  containers with their image references, command, args, env and volume mounts, the DurableDir volume names, the
  size). Volumes of other kinds are not herd's; a mount of one is refused by the plan's validation.
- **Images.** Each image reference is resolved for the host's platform (`linux/<arch>`; an index narrows to that
  platform's manifest) through `image.Source` (`image/registry`: OCI distribution over HTTPS, bearer tokens,
  anonymous or for the node's registry login, and Basic-only registries (PLT-222: Substrate's API carries no pull
  secret, so, as a Kubernetes node's container runtime does, the node holds its logins, `-registry-auth`, a docker
  config file read at every pull; never logged, printed redacted; plain HTTP only to localhost, 127.0.0.1 and the
  operator's `-insecure-registry` hosts, exactly as named, PLT-224; ahead of the node's login, a golden build's pull
  uses its template's one-shot `image_pull_auth`, A-34); a manifest fetched by digest must hash to it,
  every blob is checked against its digest). The layers are
  flattened in Go with OCI whiteouts and opaque directories into one tar (owners, modes, links and xattrs kept; an
  entry leaving the tree is a bad layer), and `image.Builder` turns the tar into a read-only filesystem without root:
  erofs with `mkfs.erofs --tar=f` (erofs-utils >= 1.7) where installed, ext4 with `mke2fs -d <tar>` (e2fsprogs >=
  1.47.1) otherwise (`mkfs.Detect`); an older mke2fs gets the tree unpacked to a directory, which keeps owners only
  when herdlet runs as root. The cache is keyed by filesystem type and the platform manifest's digest, never
  by tag. A tag is resolved once (PLT-213): the first boot of a template on a host pins each reference to the digest
  its tag named (an index's, so the pin holds on every platform), every later VM of the template, every Restart and
  every snapshot bundle (`pins`) use that digest, and a restore, fork or move builds from the bundle's pins, never
  from the tag. The cache keeps manifest records and layers by digest (`manifests/`, `blobs/`), so a pinned reference
  whose image the host has reaches no registry, and one it lacks is fetched by digest. A registry's 429 or 503 is
  retried after its Retry-After (bounded; never past the work's deadline) and then answers `image.ErrUnavailable`,
  which herd-api returns as Unavailable. zstd layers are not supported yet. The images become read-only virtio-blk disks in the order of the
  distinct images (`/dev/vda`, `/dev/vdb`, ...; Cloud Hypervisor gets `readonly`).
- **Share and plan.** Each VM has its own share `<state>/shares/<vm id>` (virtio-fs tag `herd`). herdlet creates the
  DurableDir volumes there as directories through `os.Root` (a name is one DNS label; an existing non-directory is
  refused) and writes herd-guest's plan (`.herd/actor.json`, A-10) with each container's argv by Substrate's rules
  (command replaces ENTRYPOINT and CMD, args alone replace CMD), the image's env overridden by the template's, and the
  image's working directory.
- **Warm VMs.** Substrate's ActorTemplate has no warm count, so the count is declared on the herdlet per template uid
  (`-warm <uid>=N`); the pool learns the template's spec from its first boot and keeps N VMs booted from it, reports
  the ready counts to herd-api as capacity (the scheduler prefers them, A-15), and hands one to the next boot of that
  template. A warm VM is checked (VMM present, herd-guest accepts a connection) before it is handed out and on every
  pass; one that fails is deleted and replaced, never handed out, and VMs of an outdated spec are deleted. The actor
  adopts the warm VM's id (herdlet maps actor id → VM id, also for DialGuest).
- **Snapshot bundle.** The snapshot object is a tar: a manifest (the VMM's snapshot record, the template with its
  image references and container spec, the producing platform and the manifest digests the images ran as) and the
  volume tree under `volumes/` (links kept as links, nothing followed). For a suspend the VM is stopped right after
  the VMM's snapshot and before the tree is read, so the tree is what the actor left; if the bundle cannot be made
  durable the VM is booted again from its share and the outcome is failed. A restore unpacks the tree into a fresh
  share through `os.Root` (`..`, a symlink leading out, or a volume that is itself a symlink are refused before any VM
  starts). A VOLUMES bundle cold-boots on any host, the Mac and Ubuntu alike, with the images built for that host's
  architecture from the same references; a MEMORY bundle restores only in its restore family (under the restoring actor's own VM id since
  A-28's round 3; before, under its original VM id) and is refused by the herdlet of another family before anything there is touched (the scheduler already does
  not place it there, A-15).
- **Delete.** Gone means the VMM's verified gone and the VM's share observed absent.
- **Limits.** A MEMORY snapshot's memory files stay in the VMM's snapshot directory, so MEMORY restores on the host
  that took it (or one sharing that directory and its state paths) — superseded for Cloud Hypervisor by A-28, whose
  bundle carries them; the herdlet's actor → VM map and template table
  are in memory, so a restarted herdlet does not adopt the VMs it left; with `snapstore/disk` as the snapshot store,
  hosts that move actors must share that directory with herd-api (`snapstore/s3`, A-25, removes that); a snapshot that is not a suspend (a tag) reads the
  volume tree while the guest runs.

## Decisions for R6 (deployment modes, PLT-117)

### A-20 One code path, three modes; joining is one token

**Decision.** Every component is an options struct in package `deploy` (`API`, `Router`, `Egress`, `Herdlet`) whose flags
it registers itself and whose `Run` serves it; `cmd/herd-api`, `cmd/herd-router`, `cmd/herd-egress` and `cmd/herdlet` are
one-line mains over `deploy.Main`, and `cmd/herd` (all-in-one) runs the same four in one process. A mode is
configuration only.
- **herdlet.** `deploy.Herdlet` carries A-19's wiring (Cloud Hypervisor or Virtualization.framework, the image cache over
  the OCI registry with erofs or ext4 by `mkfs.Detect`, one share per VM, warm VMs per template) and R2c's flags
  (`-state`, `-labels`, `-warm`, `-router`, `-cloud-hypervisor`, `-virtiofsd`, `-host`, ...). `herdlet join` gets its
  credentials by a join; `herdlet run` (or bare `herdlet`) dials with `-api -worker -token-file <herdlet credential>`
  as R2c did, or with the grant a join left; `herdlet doctor` prints the host checks and then what the backend
  declares. All-in-one runs this same herdlet.
- **All-in-one** (`herd -data DIR`): herd-api on bbolt (`DIR/herd.db`, A-11 — not the SQLite R-D4 names), herd-router,
  herd-egress and a herdlet. The process creates its key (`DIR/jwt.key`) and mints a join token, and its herdlet joins
  over the gRPC port exactly as a remote host does; there is no in-process shortcut.
- **Multi-host join**: `herd-api join-token` mints a join token (claim `herd_join`, nothing else granted: it cannot open
  a link or a tunnel and reads nothing). `herdlet join <herd-api> --token <t>` calls `/herd.ext.v1.Join/Join` (unary,
  JSON) with its worker name and gets a herdlet credential naming that worker, an egress credential (read in every
  space, for the host's herd-egress) and the router tunnel address herd-api advertises (`-advertise-tunnel`). The
  grant is kept in `<state>/join.json` (and `egress.token`) and reused while the worker and herd-api address are
  the same, so a join token may be short-lived. A join is refused for a token herd-api did not sign, an expired one, a
  credential that is not a join token, an invalid worker name, or a worker that is connected now.
- **Nomad**: `dist/nomad/herd-api.nomad.hcl` (service job: herd-api + herd-router, `exec`, count 1 on the `herd-data`
  host volume) and `dist/nomad/herdlet.nomad.hcl` (system job: herdlet + herd-egress, `raw_exec`; the join token comes
  from the job's Nomad variable and herd-api's address from Nomad service discovery). Nomad supervises processes;
  herd places actors.
- **Artifacts** are rendered from `deploy/artifacts/templates` into `dist/` (systemd units, launchd plists, the Nomad
  pair); a test keeps `dist/` equal to the rendering and parses every command line an artifact runs with the
  binary's own flag set. The runbooks (`docs/runbooks/`) are checked the same way. `scripts/release.sh` builds
  static linux amd64/arm64 binaries and darwin arm64 ones (herd and herdlet with cgo, on a Mac, signed for
  Virtualization.framework).
- **Snapshots** across hosts are in herd-api's S3 bucket, which the join hands every herdlet (A-25); with a
  directory store they need one directory seen by herd-api and every herdlet. `herdlet doctor` says why a host cannot join (R-D7).
- The no-dial guards of A-13 and A-16 follow the code: they scan `deploy/api.go` and `join` (herd-api), and
  `deploy/router.go`, which holds herd-router's one gRPC client (to herd-api).

## Decisions for R7 (macOS hosts, PLT-118)

### A-21 The Mac's network is gvisor-tap-vsock with herd-egress as its only way out

**Decision.** Each VM on a Mac gets its own userspace stack (`egress/gvstack`): gvisor-tap-vsock's Ethernet switch
and link endpoint (v0.8.7, vfkit framing: one frame per datagram over a unix datagram socket pair) in front of a
gVisor netstack in promiscuous mode. The netstack's only TCP handler hands every connection, to any address, to
herd-egress as an `egress.Flow` with the address the VM dialed; its only UDP endpoint is the gateway's port 53,
answered by `SyntheticDNS`. gvisor-tap-vsock's own services are not used: its forwarder is a NAT that dials what
the VM names from the host. A filter before the netstack passes ARP, TCP from the VM's address and UDP to the
gateway's port 53, and drops and counts everything else (other UDP, ICMP, IPv6, fragments, forged sources). The
VM's end of the socket pair is the `VZFileHandleNetworkDeviceAttachment` (`vz.Config.Network`); vz calls
`vz.Config.ReleaseNetwork` once the VM is verified stopped. `egress.StackNetwork` serves each flow as the VM's
actor, looked up per flow, so a warm VM booted before any actor has its flows refused until herd-api's boot names
the actor (`link.Work.Actor`; the herdlet's `OnActor`, called with the warm VM's own id when one is adopted).
Because the device is a file handle in the herdlet's process, a Mac's `deploy.Herdlet` runs herd-egress in-process
(`deploy.macHost`, behind `host_vz.go`) and reads policies with the join's egress credential. Its credential stores are
the herdlet's `-secrets` directory (`ate-secret://dir/<name>/<tail>`), which herd all-in-one hands it from its own
`-secrets` and the launchd daemons pass; a `credential_uri` is refused only when the store it names is absent
(PLT-209). Every VM uses 192.168.127.2 with gateway 192.168.127.1 (each has its own stack). herd-guest
configures that address and installs the gateway CA from the plan (`deploy.stackLink`, PLT-206). Not yet: DHCP, and keeping the in-process CA across herdlet restarts.

### A-22 A Mac declares MEMORY only while its probe passed and its console is unlocked

**Decision.** `vz.VMM.Capabilities` is MEMORY only while both hold: the save/restore probe (validateSaveRestoreSupport
and a real round trip, A-6) passed, and the console session (`vz.Session`; on a Mac `IORegSession`, which reads
IOConsoleUsers/CGSSessionScreenIsLocked and IOConsoleLocked from `ioreg -n Root -d1 -a` and needs no GUI session or
cgo) has a user with the screen unlocked. A locked screen, the login window, a session that does not answer and a
backend with no session check are VOLUMES with the reason (`vmm.Capabilities.Reason`). The probe is run again when
its result is older than `ProbeInterval` (6 h), on wake (`InvalidateProbe`), and when the console is unlocked after
a probe that ran while it was not. The herdlet re-reads its capabilities every 30 s and on each wake
(`herdlet.WakeDetector`: the wall clock outrunning the monotonic clock, which stops during sleep) and sends a change
as `link.Up.Capabilities`; herd-api replaces the worker record and the scheduler's view with it.

### A-23 macOS joins on A-20's path; the binary must carry the virtualization entitlement; each host boots its own arch

**Decision.** A Mac joins exactly as a Linux host does (A-20: `herdlet join <herd-api> --token`, the launchd daemon
`com.everdict.herdlet` from `deploy/artifacts`, which also runs Interactive with 65536 open files). `herdlet doctor`,
and so the preflight of every `herdlet join`/`run` and of `herd`, fails on a Mac unless the running binary is signed
with `com.apple.security.virtualization` (read with codesign) — Virtualization.framework refuses every VM otherwise;
`scripts/release.sh` signs the darwin herdlet with `vmm/vz/vz.entitlements` and checks the signature carries it.
`guest/build.sh all` builds the amd64 and arm64 kernels and initramfs into one directory (`herd-guest-<arch>`), which
release.sh packs per platform, the same bytes from the same source (A-44); doctor fails a host whose `-kernel` boot
header (`guest.KernelArch`) is the other architecture's. Container images are taken as linux/<host arch> from their index (`image.Platform`, A-19).

## Decisions for R8 (conformance, PLT-119)

### A-24 Conformance: one client suite, Substrate's contract wins

**Decision.** `conformance/substrateapi` (command `herd conformance`, docs/conformance.md) is a client of the pinned
`Control` subset and of the router's `ate-target-actor` ingress only; a test keeps it from importing any herd package
but the two API definitions or naming a herd-only method or header. It runs against Substrate on kind and against
herd, and where the two differ the suite follows Substrate and herd is fixed.
- A case skips only on an `Unimplemented` answer that carries a reason (the server's declaration); the move case also
  skips, as `not configured`, on a target with one worker pool. Every run prints the target's skip list.
- What the probe sends through the router is per target: `http-get:<path>` and `sandbox-process` for Substrate's
  demos, `env-exec` (agent-substrate/env's guest API) for herd-guest.
- herd fixes the suite drove: two forks of one MEMORY tag on one host — the second finds the snapshot's VM id taken
  and cold-boots from the bundle's volume tree under its own id (A-19's restore under the original id stays for the
  first); herd-router keeps a guest's trailers-only gRPC refusal trailers-only instead of flushing it as headers.
- CreateActor may answer RUNNING (herd) or SUSPENDED (Substrate); the suite resumes either way.
- Every SuspendActor names its durability mode, because Substrate defaults an unset mode to ASYNCHRONOUS (the
  snapshot may stay PENDING for minutes): the durability-checking cases send SYNCHRONOUS and require the snapshot
  COMPLETED at return; `suspend-async` sends ASYNCHRONOUS and checks the suspend only. herd still treats an unset
  mode as SYNCHRONOUS (stricter than Substrate's default; no suite case depends on it).

## Decisions for PLT-201 (a snapshot store every host reaches)

### A-25 Snapshots in S3; the join hands herdlets the store

**Decision.** `snapstore/s3` is a `snapstore.Store` in one bucket of any S3-compatible endpoint (MinIO, AWS S3),
path-style, with an in-repo SigV4 signer (checked against AWS's published test vectors) instead of an SDK. It keeps
A-15's contract: Put hashes the bytes first (a non-seekable reader is spooled to a temporary file), uploads them in
one PUT whose signed payload hash and `x-amz-checksum-sha256` make the endpoint refuse other bytes, then HEADs the
object and answers only when size, recorded digest and the endpoint's own checksum (or, without one, a re-read)
match; a failed or unknown outcome deletes the key, so Stat never reports an object after a failed Put. Verify
re-reads; Delete is verified by a HEAD. An object past one part goes up as a multipart upload with the same promises (A-35). herd-api selects it with
`-s3 s3://bucket[/prefix] -s3-endpoint URL` (credentials from `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`), and the
join grant carries the store's configuration, credentials included, to every herdlet, which uses it (A-26). The
join runbook needs no shared mount.

**Consequences.** Every joined host holds herd-api's bucket credentials (in its 0600 join state), as it holds its own
herdlet credential; a narrower per-host key is a later change. MEMORY memory files still stay in the VMM's snapshot
directory (R2's limit), so what crosses hosts through the bucket is the VOLUMES bundle (until A-28, which puts Cloud
Hypervisor's memory files in the bundle). The Nomad pair still used a directory store until A-26.

## Decisions for PLT-202 (a joined herdlet's -snapshots)

### A-26 A join's S3 store wins over -snapshots; no shipped herdlet join passes one

**Decision.** A herdlet whose join grant names an S3 store keeps snapshots there whatever `-snapshots` says, and logs
a warning naming the ignored directory: herd-api verifies every snapshot in its own store, so a herdlet writing
elsewhere fails every suspend ("snapshot not durable"), as the systemd unit's herdlets did on the first real join
(2026-10-31). Ignoring rather than refusing keeps a host that upgrades the binary under an older unit running.
`-snapshots` still serves a herd-api without `-s3`, whose grants name no store. The systemd unit and the Nomad herdlet
job pass no `-snapshots` (the launchd daemon never did), and the Nomad herd-api job takes `-s3` and its credentials
from its Nomad variable, so the Nomad pair needs no shared directory either.

## Decisions for PLT-211 (virtiofsd on Ubuntu LTS)

### A-27 herd ships its virtiofsd; doctor checks the one it is given accepts herd's options

**Decision.** The Linux release archives carry a static virtiofsd (`virtiofsd`, musl, static libseccomp and
libcap-ng), built by `scripts/virtiofsd/build.sh` from the upstream tag `scripts/virtiofsd/source.env` pins (1.13.2,
gitlab.com/virtio-fs/virtiofsd at commit 720245d0; the build refuses another commit and builds with `cargo --locked`,
so every crate matches Cargo.lock's checksums) the way upstream's CI builds its static binary. `scripts/release.sh`
refuses to pack one that does not match the checksum the build recorded, the pinned version or the archive's
architecture. The runbooks install it at `/usr/local/libexec/herd/virtiofsd`, which is herdlet's default
`-virtiofsd`, and the systemd units and the Nomad herdlet job (from its task directory) use it; `-virtiofsd` still
takes an operator's own. Why: herd starts virtiofsd with `--migration-mode=find-paths` (and `--readonly` for a
read-only share), which need >= 1.11, and Ubuntu 24.04 LTS's `virtiofsd` package is 1.10. Following the runbook's
`apt-get install virtiofsd` on a fresh 24.04 host (2026-10-31) gave a host whose doctor said ok and whose every boot
failed: virtiofsd exited on the unknown option before making its socket. `herdlet doctor` therefore runs the given
virtiofsd's `--help` and fails, naming the missing options and the fix, unless every option herd passes is listed:
the options come from `cloudhypervisor.VirtiofsdArgs`, which the backend starts virtiofsd with, plus
`-virtiofsd-args`. herdlet's preflight runs doctor, so a herdlet (and the all-in-one) given such a virtiofsd refuses
to start rather than join and fail every boot. Checking the options rather than a version number keeps the check true
to what is passed and works for a distribution build that reports its own version.

## Decisions for PLT-212 (a MEMORY snapshot restores on any host of its family)

### A-28 A MEMORY bundle carries the hypervisor's snapshot files

**Decision.** A VMM whose snapshots can travel implements `vmm.SnapshotCarrier`: `ExportSnapshot` lists the files
of a snapshot it took, `ImportSnapshot` keeps carried files as that snapshot on its own host so `Restore` finds it.
For a MEMORY snapshot of such a VMM, herdlet writes those files into the bundle (version 2) between the manifest and
the volume tree, as `memory/<name>`, and names them with their sizes in `Manifest.Memory`. The bundle is the one
object herdlet puts in the snapshot store and herd-api verifies by digest before it records the snapshot durable, so
a durable MEMORY snapshot now holds everything a restore needs, on any host of its restore family, also after the
host that took it is gone. A restore of a MEMORY bundle hands the files to `ImportSnapshot` inside the share's fill,
after the link and the share were claimed (so of two forks at once on one host with links, only the one that gets the
snapshot's link reads it; the other skips the files and cold-boots), and only then calls `Restore`. Cloud Hypervisor implements it: the export is
the published snapshot directory (config.json, state.json, memory-ranges and herd's record); the import writes the
files into a partial directory, checks that herd's record among them names the reported snapshot (id, VM id,
fidelity, family) and publishes it by rename, as a snapshot it took; a snapshot already published there is kept.
The fake VMM implements it too (its record is its one file), and each test host gets a snapshot store of its own,
so a test that crosses hosts at MEMORY exercises the carriage instead of a store the hosts share.
- **Not carried.** A VMM that is not a carrier (vz: the save file is sealed to one Mac and user, whose restore
  family is that Mac, A-8) writes a bundle without memory files, which restores at MEMORY only where the files are;
  the scheduler already places it only in that family. A version 1 bundle (written before this) carries none either.
  A MEMORY restore of such a bundle on a host that does not hold the files fails and says so ("the bundle carries
  no memory files ... and this host does not hold them"); it is never turned into a VOLUMES cold boot.
- **Consequences.** A MEMORY bundle is about the guest's memory size larger (512 MiB for the default VM), which the
  herdlet spools to a temporary file and uploads once per snapshot (in parts past 64 MiB, A-35), leaving out the memory
  files' zero pages (A-35). The
  taking host still keeps its own copy in its vm-snapshots directory (nothing deletes VMM snapshots yet).
- **Host paths (round 2).** The config Cloud Hypervisor saves with a snapshot names the taking host's paths: kernel
  and initramfs (under a Nomad allocation's task directory, different on every client), disk images, virtio-fs and
  vsock sockets, serial and console files, and the NIC's TAP and MAC. A MEMORY restore therefore restores from a
  copy in the new VM's own directory (`restore/`): config.json rewritten to the restoring VM's spec (disks by
  position, shares by tag; unknown fields kept; a snapshot whose device set differs is refused with
  `vmm.ErrInvalidSpec`), the other files linked. Hosts need not share a `-state` path. The NIC keeps the snapshot's
  link (the guest's memory has its address): the restoring host claims the same lease (A-18) or the restore
  cold-boots on a link of its own, as before.
- **Forks (round 3).** A MEMORY restore runs under the restoring actor's own VM id, its own share and its own sockets
  (the rewritten config names them), never under the snapshot's: a fork ran under its parent's VM id before, so on
  the fork's host any work for the parent's id (a release, an inspect) reached the fork's VM, and herd-api and the
  herdlet named one VM by two actors. What one guest address allows is decided by the link: the fork claims the
  snapshot's link (TAP, MAC, guest address) under its own id; on another host that is free and the fork resumes the
  memory with the parent's address on a TAP of that host (separate L2, no conflict with the parent's); on the
  parent's host, or where another fork of the tag holds it, the claim fails and the fork cold-boots on a link of its
  own. On a host whose VMs get no link there is no address to keep apart: every fork resumes the memory. A memory
  taken with a link restored where VMs get none (or the reverse) cold-boots, since Cloud Hypervisor refuses a
  device set other than the snapshot's.
- **Evidence.** A VM that fails to start or restore has the tail of every log in its directory (cloud-hypervisor's
  stdout and stderr, virtiofsd's, the serial console) logged by the herdlet, and how cloud-hypervisor ended plus its
  log's last lines in the error herd-api records, before the directory is removed. Since round 3 Cloud Hypervisor
  runs with `-v` (its info-level steps, e.g. which device it was restoring, go to its stdout and stderr), an empty
  log is said as such, the kernel's messages about the process (/dev/kmsg: an OOM kill, a segfault) are logged, and
  every delete herd asks of a VM and every signal it sends a VMM is logged, so a VMM herd itself ended is told from
  one that died. The supervisor's second Nomad walk
  (2026-10-31) saw only `vm.restore ... EOF`: CH died during a cross-node restore and its log went with the
  directory.
- **Real host.** `TestRealHostMemoryAcrossHerdlets` (HERD_MEMORY_REAL=1) runs two herdlets with separate `-state` on
  one KVM host, joined to one herd-api over S3. Since round 3 a third herdlet gives its VMs real TAP links and
  restores MEMORY forks and suspends with their NIC from the bundle; a cross-herdlet MEMORY restore with a NIC is not
  possible on one host (both herdlets name TAPs herd<slot>, and the guest's address is held by the source's pool),
  so that path is covered on one herdlet after its vm-snapshots are removed, and across hosts by the Nomad walk.

### A-29 Each VM runs in a herd-owned cgroup of its own, outside the herdlet's

**Decision.** The Cloud Hypervisor backend gives every VM a cgroup v2 directory `/sys/fs/cgroup/herd/<vm>` (`-vm-cgroup`,
`cloudhypervisor.CgroupV2` behind the `Cgroups` interface) and starts the VM's cloud-hypervisor and virtiofsd in it
with `CLONE_INTO_CGROUP`, so not one page is charged to the herdlet's cgroup. The memory controller is enabled from
the root down to `herd`; each VM's `memory.current` accounts for it and its `memory.max` is the guest memory plus
`-vm-memory-overhead` (512 MiB by default: the VMM, virtiofsd, page cache). The cgroup is removed with the VM, also
after a failed start. Doctor (and so every herdlet's preflight) checks a probe cgroup can be made there and that
`herd` is not inside the herdlet's own cgroup; `-vm-cgroup ""` keeps the old placement and says so.
- **Why (PLT-214).** Under Nomad raw_exec every process the herdlet started lived in its task's cgroup, which Nomad
  limits to the task's memory (300 MB when the job declares none). A MEMORY restore copies the whole guest memory into
  shared memory at once, so the memcg OOM killer SIGKILLed Cloud Hypervisor mid `vm.restore` (the client saw EOF). A
  bigger task limit would be wrong too: the VMs' memory is herd's capacity (`-slots`), not the herdlet's. The herdlet
  job now declares resources for the herdlet process alone; the systemd units set no MemoryMax.
- **Lifecycle.** Outside the task or unit cgroup, stopping the herdlet would no longer end its VMs, and a restarted
  herdlet does not adopt the VMs it left (A-19, Limits); processes started in a VM cgroup therefore carry
  `PR_SET_PDEATHSIG` SIGKILL, so a VM ends with the herdlet process as it did in its cgroup.
- **Not here.** Nomad's scheduler does not see the VMs' memory; on a client shared with other jobs, reserve it in the
  client's `reserved` block. CPU and I/O controllers are not set per VM.

## Decisions for PLT-221 (golden snapshots of templates)

### A-30 herd-api builds a template's golden snapshot as Substrate's template reconciler does

**Decision.** herd-api serves `ActorTemplate.status.golden_snapshot_status` the way Substrate does at the pinned commit
(6d7b3f49: `cmd/ateapi/internal/controlapi/template_reconciler.go`, `cmd/ateapi/internal/defaults/defaults.go`,
`CreateActor` in `controlapi/actor.go`), in `apiserver/golden.go`:
- **Mode.** CreateActorTemplate stores an omitted `snapshot_config.golden_snapshot_config` or mode UNSPECIFIED as
  ENABLED (Substrate's `defaults.Apply`), so a template reads back with the mode it is built by; status starts empty
  and is the server's (a client's status is dropped). Every mode but DISABLED builds a golden snapshot (Substrate's
  reconciler skips only DISABLED). `GoldenSnapshotStatus` has no mode field: a DISABLED template reports DISABLED as
  its `golden_snapshot_config.mode`, carries no `golden_snapshot_status`, and its actors boot cold.
- **Build.** A golden pass, started by CreateActorTemplate and continued by every `Reconcile`, holds the template's
  lock and re-derives its next step from what exists, so each step is reentrant: the golden actor is named by the
  template's uid in its atespace, created like any actor (its boot is the template's one boot) on the worker keeping
  the highest `suspend_max_fidelity` (`sched.Request.PreferFidelity`); `snapshot_time` is set to the end of the
  warmup (`-golden-warmup`, Substrate's 20 s by default; a timer resumes the pass then); then CreateTag snapshots the
  running golden actor in place, at the template's preferred fidelity capped by what the worker keeps (A-14), into a
  TAG_SCOPE_PUBLISHED tag of the same name; the golden actor is deleted (verified, A-14) and only then is
  `golden_tag` recorded. A pass that finds the tag again (a failure between the tag and the status write) records it.
- **Failure is said, and retried (A-35).** A boot the herdlet refused for good (`GoldenActorInvalid`), a snapshot it refused
  (`GoldenSnapshotFailed`), a crashed golden actor (`GoldenActorCrashed`), a tag of another template under the name
  (`GoldenTagConflict`) or a golden actor in a state the build never makes (`GoldenActorUnexpectedState`) end in
  `error_message` `<Reason>: <detail>` (at most 4096 bytes), and the golden actor is let go; Reconcile builds it
  again after a doubling backoff, five times at most (A-35); a golden whose guest no connected worker runs any more
  is built again behind it (A-38). What can still succeed (no
  worker connected or free, a registry answering 429, an unknown herdlet answer) stays owed: it is logged, counted by
  `Reconcile` as owed, and retried; it never becomes an error the client reads as terminal.
- **Use.** CreateActor without `source_tag` from a template with a golden tag restores from the tag's snapshot (a
  missing tag is FailedPrecondition, as on Substrate). herd answers the actor RUNNING, as for any create (A-24). Where
  no worker can restore it (a MEMORY golden snapshot and a selector or pool outside its restore family), the actor
  boots cold instead of being refused: the golden snapshot is a start-up state, not the actor's own.
- **Delete.** DeleteActorTemplate deletes the golden actor and the golden tag (and its snapshot object) before the
  record; the golden actor does not count as an actor using the template; a tag other than its golden that holds the
  template's uid refuses it, as an actor does (A-41).
- **Not here.** `golden_egress_policy` is stored but not applied: the golden actor runs under the default-deny egress.
  Wakeup probes are not served by herd, so the warmup is always the configured one (Substrate takes none when every
  container has a wakeup probe). Warm VMs (`-warm`) serve cold boots only, so a template with a golden tag no longer
  draws on them. herd's own workflow tests pin cold-boot paths (slots, owed steps, image resolutions) and create
  their templates DISABLED; the Substrate-API suite keeps the default.

## Decisions for PLT-227 (restoring a golden over a slow S3 link)

### A-31 A node restores a bundle it holds from its own disk; a restore's call waits for the bytes it moves

**Decision.** A herdlet whose snapshots are in S3 (a join's store, A-25) keeps every bundle it put in the store and
every bundle it read from it in `<state>/bundles` (`snapstore/bundlecache`), under the object's digest, bounded by
`-bundle-cache` (MiB, 20 GiB by default, 0 for none) and evicting the least recently used. A restore names its
object by key and digest (A-14): a node that holds the digest restores from its file and reads nothing from the store;
one that does not reads the object once, hashing as it writes it to disk, refuses it unless it is the digest, keeps
it and restores from it (the restore used to read it twice, a Verify and then an Open, and keep neither). Restores of
one digest at once on a node wait for one read. A herdlet on a disk store (all-in-one, a shared mount) keeps no cache.
herd-api bounds a restore's herdlet call by `-call-timeout` plus the object's size (a Stat of it) at
`-restore-bandwidth` (MiB/s, 8 by default), the slowest rate a node is expected to read the store at, so a node that
must fetch a golden is not cut off by a timeout sized for calls that move no bytes and the create answers RUNNING. A
snapshot's call waits for the bytes its herdlet reports the same way (A-35).

**Why.** On the cluster each restore of a template's golden re-read it from the control host's minio over the
tailnet, twice, under the fixed 30 s call: every CreateActor from a golden answered unknown and the actor completed
afterwards as an orphan, while the all-in-one's local store restored it in 618 ms.

**Not here.** A create whose client deadline is shorter than the sized call still ends the call with the client's
context (unknown, owed, completed by Reconcile). The cache trusts the files it wrote: a disk that corrupts one is not
detected at restore.

## Decisions for PLT-229 (an egress policy write in force when acknowledged)

### A-32 herd-egress decides on a policy read within a lease; herd-api waits out the lease before it answers a narrowing write

**Decision.** herd-egress decides on an actor's policy only if its last read of it started within `egress.PolicyLease`
(1 s); a decision past that reads it again first (one read per actor at a time, joined by every decision that a
read in flight satisfies). A refusal is decided again on a read that started after the decision began. Either read
waits at most `Syncer.Wait` (2 s), after which the decision is made on what the actor has. herd-api's
`UpdateActorEgressPolicy` and `DeleteActorEgressPolicy` wait `PolicyLease` after the write before they answer, so any
read a herd-egress can still decide by started after the write: the write is in force on every herd-egress serving
the actor when it is acknowledged, whether herd-api is one process or several and without knowing which hosts serve
the actor. `CreateActorEgressPolicy` does not wait: it can only widen a deny-all, and a refusal reads again. The
periodic sync (A-18, every `-interval`) stays and keeps most decisions from reading inline.

**Why.** everdict-herder creates the policy right after CreateActor and the control plane's first exec follows at
once; herd-egress polled every 1 s, so on the cluster an actor's flows were refused "no rule allows tls" for 1-2 s
after the policy was acknowledged and a session could fail its first git clone. Push with acknowledgement would need
herd-api to know each herd-egress and a new API; the lease needs neither and covers a narrowing write too.

**Not here.** A read that fails keeps the last policy (A-18: unknown is not absent), so a herd-egress cut off from
herd-api can decide by a policy a narrowing write has replaced; the lease bounds staleness only while reads answer.
An actor that keeps hitting a refused host costs herd-api one read per refusal round (reads for one actor are
serialized). Deleting an actor deletes its policy without the wait.

## Decisions for PLT-230 (images whose entrypoint switches user)

### A-33 Containers run as Docker runs them; a container that ends crashes its actor, with its status and output

**Decision.** herd-guest writes each container's process with Docker's default capability set (CHOWN, DAC_OVERRIDE,
FSETID, FOWNER, MKNOD, NET_RAW, SETGID, SETUID, SETFCAP, SETPCAP, NET_BIND_SERVICE, SYS_CHROOT, KILL, AUDIT_WRITE) as
its bounding, effective and permitted sets, nothing inheritable or ambient, and keeps noNewPrivileges (the template
API has no field that turns it off). The process runs as the image's USER, resolved against the image's own
`/etc/passwd` and `/etc/group` by Docker's rules (`oci.ResolveUser`: a name must exist, a numeric uid need not and then
runs with gid 0, the user's groups are its additional gids unless a group is named), in its WORKDIR, cleaned. crun
exec takes the container's user, so exec records are handed to it. The container's init (`cinit -report`) gets two
pipes through `crun run --preserve-fds 2`: its command's stdout and stderr go to the first, and its status to the
second, which only the init holds, so its close is the init's end. herd-guest keeps the last 20 lines (2 KiB) of
output. When a container's main process ends, herd-guest logs it, appends it (status and last output) to
`.herd/container-exit` in the share, and answers an exec into that container FAILED_PRECONDITION naming the exit. The
herdlet's exit watch reads that file for every VM it runs (on hosts whose hypervisor cannot report exits too) and
reports `container-exited`; herd-api moves the RUNNING actor to CRASHED with the guest's account in the crash message,
and herd-router refuses a request to a CRASHED actor at once with FAILED_PRECONDITION (`actor-crashed`) and that
message instead of parking it. The VM runs until the actor is deleted.

**Why.** crun grants a process whose spec has no capabilities none at all, so root in the container could neither
chown nor setuid: redis:7-alpine (docker-entrypoint.sh: chown, su-exec redis) and nginx:1.27-alpine (workers setuid to
nginx) exited right after boot, and every exec answered INTERNAL "the container `box` is not running", with nothing
saying why. The VM is the isolation boundary, so Docker's default is the compatible choice.

**Not here.** A template's `security_context.capabilities` (add/drop) changes this set: A-40.

## Decisions for PLT-330 (a template's image pulled with a one-shot credential)

### A-34 A template carries a one-shot pull credential for its golden build; the node's registry login is the fallback

**Decision.** `CreateActorTemplateRequest` gains herd's own field `image_pull_auth = 1000` (a string): a docker config
file's `auths` as JSON, the format `-registry-auth` already reads (per registry host `auth`, base64 of
`user:password`, or `username` and `password`, or `identitytoken`). It is the smallest shape that names the registry
host, both login forms and several hosts at once, and the herdlet parses it with the code that parses the node's file.
- **In the API.** The field is appended to the upstream message by `internal/cmd/protosubset -additions
  api/ateapi/v1/herd-additions.txt`, marked "herd addition"; herd's field numbers start at 1000 so a field upstream
  adds later never collides, and a real Substrate ignores it (an unknown field). No `ActorTemplate` field carries it,
  so GetActorTemplate cannot return it (a test walks every field a read returns). `ateapi.pb.go` is protoc 36.2 and
  protoc-gen-go v1.36.12 output (both fetched from GitHub as build tools; they reproduce the previous file byte for
  byte).
- **herd-api.** CreateActorTemplate refuses with INVALID_ARGUMENT, quoting nothing of it, a value that is not such a
  JSON, that holds no login for the registry of any of the template's images, or that comes with a template whose
  golden mode is DISABLED (there is no build to use it for). Otherwise it is kept in herd-api's memory by template uid,
  never in the store, and put on the `link.Work` of the golden actor's boot (`PullAuth`, a `link.Secret`, which prints
  redacted). It is dropped when the golden build ends (tag or error) or the template is deleted. A herd-api restarted
  in the middle of a build has lost it, and the build goes on with the node's logins.
- **herdlet.** That boot's pulls (`registry.WithLogins` on its context) answer a registry's challenge with the
  template's login for the hosts it names, ahead of the node's `-registry-auth`, and keep the tokens it earns with that
  boot: a later pull without the credential does not reuse them. A host it does not name gets the node's login, if any.
  A 401 or 403 from the realm fails the golden build (`GoldenActorInvalid`) naming the registry and "the template's
  image_pull_auth", never the secret. Without the field, everything is as before.

**Why.** A template's image is pulled once, when its golden snapshot is built, and actors then start from that
snapshot, so a credential the control plane mints per session needs to live only for that pull. A node login
(`registry_auth` in the Nomad variable) leaves a long-lived token on every node; on 2026-11-05 herd answered `403
Forbidden (anonymous: this node has no login for ghcr.io)` for the first-party delegate image because no node had one.

**Not here.** The credential covers the golden build's pull only. A node that later restores the golden snapshot or
cold-boots the template without the image's layers in its cache pulls by digest with its own login. That happens for
templates whose golden mode is DISABLED, for a golden snapshot that cannot be placed and boots cold, and for a restore
on a herdlet other than the one that built the golden. Those still need the node's `-registry-auth` until a later change
carries the bytes or the credential there.

## Decisions for DEFAUL-1601 (snapshots at any size)

### A-35 A snapshot stores at any size, its call waits for its bytes, and a failed golden is built again

**Decision.**
- **Multipart.** `snapstore/s3` uploads an object larger than its part size (`Store.PartSize`, 64 MiB by default,
  raised for an object that would need more than 10,000 parts; at most S3's 5 TiB) as a multipart upload, with A-25's
  promises kept: the first pass hashes the whole object and each part; each part goes up with its own signed payload
  hash and `x-amz-checksum-sha256`, so the endpoint refuses a part that is not those bytes; the upload is created with
  `x-amz-checksum-algorithm: SHA256` and the herd digest as metadata; after CompleteMultipartUpload (whose 200 is read
  for a result, since S3 can answer 200 with an error) the HEAD must report the size, the herd digest and the
  endpoint's composite checksum (the SHA-256 of the parts' SHA-256s, `-<parts>`) of what it stored, or, from an
  endpoint that keeps none, a re-read must match. A multipart Put that fails aborts its upload (the endpoint keeps an
  open upload's parts out of Stat's sight) and then deletes the key as any failed Put does. An object up to the part
  size is one PUT, as before. The signing is the store's own SigV4; no SDK.
- **A snapshot's deadline follows its size.** The herdlet reports its bundle's size as it is written (at most every
  second) and in full before the upload (`link.Progress`); herd-api waits a snapshot's call for `-call-timeout` plus
  the most it reported at `-restore-bandwidth`, as a restore's call waits for its object's size (A-31), and sends
  the herdlet each later deadline (`link.Extend`), which moves the herdlet's own deadline for the work
  (`DeadlineUnixMilli`). A herdlet that reports nothing, or stops reporting, is cut off at the deadline it has; an
  unknown answer stays owed, never failed (R-D6). `-call-timeout` is again the bound of a call that moves no bytes,
  and the Nomad job no longer sets it (it set 10m by hand for a 4 GiB golden).
- **A failed golden is built again.** A golden build that ends in `error_message` (A-30) records a retry in the
  template's state, and the message says when (`... (herd-api builds it again at <time>, retry n of 5)`); once it is
  due, `Reconcile` clears the error and `snapshot_time` and runs the build from the start, with no change to the
  template. Retries come 1, 2, 4, 8 and 16 minutes after each failure (`apiserver.Config.GoldenRetries`,
  `GoldenRetryBackoff`); after the fifth the error stays, saying its retries failed, and nothing more is asked of a
  herdlet. A transient failure (a golden actor lost when herd-api restarted, a refused snapshot) heals; a permanent
  one ends in at most six builds. A golden actor that is still being deleted when a retry is due is waited for.
- **Zero pages.** A MEMORY bundle carries each memory file that has zero pages (4 KiB) as a PAX 1.0 sparse tar entry
  whose holes are those pages; `archive/tar`'s reader, which every herdlet already reads bundles with, gives them back
  as zeros, so the bundle's version and the restore are unchanged. archive/tar's writer writes no sparse entries (it
  drops `GNU.sparse.*` records), so the herdlet writes the entry's PAX header itself. A map that would pass the
  reader's 1 MiB bound has its closest data runs merged. A file with no zero page is written dense, as before.

**Why (measured).** On the cluster (2026-11-06) a 6.5 GB snapshot failed with "bytes is more than one PUT takes"; a
4 GiB golden took 2m51s to 3m03s and answered unknown under the fixed 30 s call; and a template whose golden failed
(GoldenSnapshotFailed, or its VM lost when herd-api restarted) stayed failed until its spec changed. Measured on this
box, which runs no VM (no KVM), on a synthetic 512 MiB memory image whose 1 MiB runs are zero with p=0.85, against an
in-process S3 endpoint over loopback:
- Store, before (one PUT) and after (64 MiB parts): 536,870,912 bytes stored either way; Put 2.0 to 2.7 s/GiB before,
  3.3 to 4.2 s/GiB after, the difference being mostly the fake endpoint's own copying of parts and a second SHA-256
  pass on the client; a read 0.37 to 0.42 s/GiB both. Past 5 GiB, before stores nothing.
- Bundle, dense (before) and sparse (after): 536,873,472 bytes against 76,551,168 (14%); written in 0.55 to 0.67 s/GiB
  against 0.16 to 0.20; a restore's read of the memory file into a synced file 0.51 to 0.52 s/GiB against 0.44 to
  0.45. With no zero page the sparse writer costs 0.05 s/GiB more and stores the same bytes. Finding zero pages costs
  0.04 s/GiB; flate at its fastest stores about as little as leaving them out but takes 0.5 s/GiB, so it is not used.
  At the cluster's measured upload rate (4 GiB in about 3 minutes) every byte left out saves about 44 s/GiB.

**Not here.** Parts go up one at a time; parallel parts would raise a single slow link's rate and are a later change.
The share of a real guest's memory that is zero was not measured here (no VM on this box): the bytes saved on a
real golden are the supervisor's to measure. A Cloud Hypervisor restore still writes the zeros of a hole into its
memory file. The snapshot the VMM itself writes to local disk before the bundle reports no progress and stays within
the plain call timeout.

## Decisions for DEFAUL-1595 (a restored VM's wall clock)

### A-36 A guest that runs on from a snapshot's memory is handed the host's wall clock before it serves

**Decision.**
- **The channel.** herd-guest serves `herd.ext.v1.ClockService/SetClock` (`api/herdext/v1/clock.proto`) beside Sync,
  on the guest port, through the same guest dialer (`machine.GuestClock`, the model being `machine.GuestFlush`).
  herdlet dials the guest until it answers and only then reads its own clock, so the time it hands over is not stale
  by the dial's retries; the guest steps `CLOCK_REALTIME` (`clock_settime(2)`, herd-guest being the VM's PID 1 as
  root) and answers the clock it replaced, which both sides log as the step. protoc and protoc-gen-go were not
  available where this was written: `clock.pb.go` is written by hand in protoc-gen-go v1.36.12's shape, its
  descriptor built with `descriptorpb`, and `TestClockProtoDescriptor` holds it to the .proto; `go generate ./api`
  replaces it with the generator's own. The service descriptor is hand-written as A-12's are.
- **Every path a guest runs on from memory.** `Machines.Restore` of a MEMORY snapshot sets the clock before it
  answers, so before herdlet reopens the VM to the router and before any exec or turn can reach it. That is every
  restore of memory: a session from a template's golden, the resume of a suspended actor, a fork from a tag, a move
  to another host. A VM a snapshot paused and left running (a golden's or a tag's source) is set after the snapshot:
  Cloud Hypervisor keeps the guest's kvmclock across a pause and puts the saved one back on resume and on restore,
  which is why a restored guest reads its snapshot's time and a fresh golden read 20 s behind. A warm VM is set when
  it is taken from the pool, since it may have waited long on a host whose clock moved. A cold boot (`Boot`,
  `Restart`, a VOLUMES restore, a MEMORY restore that cold-boots) is not set: its kernel reads the host's time as it
  boots.
- **A failed set.** A MEMORY restore whose guest does not take the clock (it does not answer within
  `Config.ClockTimeout`, 10 s by default, or its set fails) is refused: the VM is stopped and the restore fails with
  why, as a boot that fails does, because nothing else would ever correct that clock and a session on it stamps its
  traces and commits wrong and checks certificates against the wrong time, silently. A warm VM that does not take it
  is discarded and not handed out, as one failing its health check. The one exception is a guest whose herd-guest
  answers Unimplemented, one a MEMORY snapshot taken before this change kept: it is restored and logged as left on
  its snapshot's clock, with the remedy (rebuild the snapshot), because refusing it would make every golden built
  before this change unrestorable. A VM a snapshot paused is logged, not refused: the snapshot is whole, and failing
  it would not set the clock either.
- **Backwards and Go's clocks.** The clock is stepped to the host's whichever way: a host whose own clock was stepped
  back is followed, and the step is logged with its sign. Only the wall clock moves; `CLOCK_MONOTONIC`, which Go's
  timers, `time.Since` and the deadlines herd-guest arms read, does not, so a step does not fire or stall a process
  timeout. A process that measures time with the wall clock sees the step, as it would under NTP.

**Why (measured).** Live on 2026-11-06, in a box restored from a golden `date -u` read 07:32:18 while the host read
07:44:42, and a fresh golden read 20 s behind: the offset is the snapshot's age. On this box (no KVM) the fake host
`vmm/fakeguest` runs the real herd-guest and models a MEMORY restore as running on from its snapshot's clock;
`TestSessionsReadTheHostsClock` (deploy, through herd-api and `herdlet run`'s machines) reads a session from a
golden aged 72 h, its resume 12 min after the suspend, a fork and the paused source within a second of the host's
after the change, and 72 h, and 20 s for the source, behind with it taken out. The step the guest logs on the fake is
about 1 ms over a unix socket.

**Not here.** A cold boot's clock on Virtualization.framework, and the step a real Cloud Hypervisor guest logs, are
for the supervisor's hosts to read. herdlet's VMM-only path (a herdlet with no machines, which has no guest
channel) sets no clock.

## Decisions for DEFAUL-1606 (a golden built by an older guest)

### A-38 A golden records the guest that built it, and one no worker's guest matches is built again behind the old

**Decision.**
- **The guest.** A herdlet names the guest build it boots by its files: `deploy.GuestIdentity` is the SHA-256 of the
  SHA-256s of `-kernel` and `-initrd`, each named by its role, computed at start and logged. It is declared with the
  capabilities (`link.Capabilities.Guest`), so every herdlet of one release names the same guest wherever it is
  installed and nothing in a release or a job has to carry it. A herdlet that cannot read the files declares none.
- **The record.** A tag taken from a running actor records the guest of the worker that snapshotted it (the tag
  record's state); when a golden build or rebuild records its tag, the template's state records that guest as its
  golden's. A golden built before this change records none (`""`).
- **When a golden is stale.** At least one worker is connected and none of the connected workers runs the golden's
  guest. A pool that runs both guests during a rolling upgrade keeps the old golden while any worker runs its guest
  (restores of it work everywhere they did), and rebuilds it once the last old worker is gone. Herdlets from before
  this change declare `""`, as do the goldens they built, so a herd-api upgraded ahead of its herdlets rebuilds
  nothing until they follow; then every golden built before is rebuilt once.
- **The rebuild.** Only `Reconcile` begins one, in its template loop (serialized), at most `Config.GoldenRebuilds` (2)
  in progress at a time over all templates; a rebuild waiting out a retry's backoff holds its place. Rebuild n's
  golden actor and tag are named `<uid>-<n>`, so the old tag is untouched; the build's steps are A-30's, with its
  warmup end, failures and retry kept in the template's state rather than its status. `status.golden_tag` goes on
  naming the old tag, and CreateActor goes on restoring from it, until the new tag exists; then one store write names
  the new tag in status, records its guest, ends the rebuild and lists the old tag as replaced. The template's spec,
  name and uid never change, and no profile or client is involved.
- **Failure.** A rebuild that fails leaves the old golden serving and no `error_message` in status (the template did
  not fail; a client reading it would refuse a working template). It is built again on A-35's terms (the same
  `GoldenRetries` and doubling `GoldenRetryBackoff`); after the last retry it ends, its reason kept in the template's
  state and logged. A rebuild begins at most once for each set of guests the connected workers run (recorded when it
  begins), so neither a failure nor a pool that keeps two guests can make it loop; a later release, being another
  set, tries again.
- **The old golden.** A replaced tag (and its snapshot object) is deleted by a later pass once `CallTimeout` has
  passed since the swap (a CreateActor that read the old tag before it has recorded its actor by then) and no actor
  owes a start from its snapshot. An actor already started from it does not need it. DeleteActorTemplate deletes
  every golden actor and tag of the template: its first, the current, a rebuild's and replaced ones not yet deleted.

**Why.** Walked live on 2026-11-06: herd v0.1.6 fixed `/tmp` in the guest, and a resume still failed because it
restored from a golden v0.1.5 had built. A template's name is a hash of its spec, so no upgrade invalidated its golden,
and an operator had to change a resource value to get a fresh one.

**Proof here (no KVM).** `conformance/goldenguest_test.go` runs herd-api with fake herdlets that declare a guest and
restarts one on another, as an upgrade does: the golden is rebuilt with no change to the template, and actors start
from the new one, the old tag goes (`TestUpgradedGuestRebuildsGolden`); during the rebuild the template names the old
golden and an actor restores from it (`TestOldGoldenServesUntilRebuildReady`); a rebuild whose snapshots are refused
keeps the old golden with no error and stops after its retries (`TestFailedRebuildKeepsOldGolden`); three stale
templates rebuild one at a time under a bound of one (`TestGoldenRebuildsBounded`); a restart on the same guest, and
a pool with both guests, rebuild nothing, and the end of the rolling upgrade rebuilds once (`TestSameGuestRebuildsNothing`).
`deploy.TestGuestIdentityNamesTheGuestBuild` holds the identity to the files' bytes and roles.

**Not here.** The rebuild's pull carries no `image_pull_auth` or `image_plain_http_hosts` (A-34, A-37 keep them in
memory for the first build only): a rebuild on a node without the image's layers pulls with the node's own login and
`-insecure-registry`, and if it cannot, it fails, and the old golden keeps serving. A golden copied from a suspended
golden actor records no guest. The guest is not shown in `ListWorkers` or `GetWorkerCapabilities` (their protos have
no field for it); herd-api reads it from the live registrations. The bound is not a herd-api flag. Rebuilding on a
real upgrade of Cloud Hypervisor hosts is the supervisor's to walk.

## Decisions for DEFAUL-1610 (a tag copies its snapshot through herd-api)

### A-39 A copy within the store is server-side, and a store's checksum proves an object without a re-read

**Decision.** Superseded for tags by A-45: a tag of a suspended actor references the actor's sealed object
and copies nothing. Copy stays a store capability, and Prove the suspend's check.
- **Copy.** `snapstore.Store` has `Copy(from, to, digest)`: it answers only once the copy is durable and holds
  exactly digest's bytes, and a Copy that fails leaves nothing under `to`. CreateTag of a suspended actor
  (`apiserver` `copySnapshot`) is a Copy, and no longer a Verify, an Open and a Put through herd-api.
- **S3 copies in the bucket.** `snapstore/s3` HEADs the source (its herd digest must be the one asked for), then
  copies it with one CopyObject up to `Store.MaxCopySize` (S3's 5 GiB), and past that with UploadPartCopy, in the
  source's own parts (their size from a HEAD of part 1, `?partNumber=1`). Both are signed with the store's own SigV4;
  there is still no SDK. The copy's metadata is the herd digest (`x-amz-metadata-directive: REPLACE`) and it asks
  for a SHA-256 checksum. Like Put, a Copy that fails aborts its upload and deletes the key.
- **The proof is a HEAD.** The copy must report the source's size and herd digest, and the endpoint's own checksum
  of what it stored must agree. A CopyObject's checksum is a full-object SHA-256, so it must be the digest itself.
  A part copy's is S3's composite one; built from the source's parts, it must be the source's composite checksum,
  which the copy records as `X-Amz-Meta-Herd-Checksum`. Only an endpoint that keeps no checksum has the copy read.
  A source that is not made of parts a copy can repeat is copied in the store's parts and proved by a read.
- **Which errors fall back to streaming.** These answers mean the endpoint does not implement the copy:
  - HTTP 501 or 405.
  - A 4xx with code NotImplemented, MethodNotAllowed, InvalidRequest or InvalidArgument.
  - A 2xx without a `CopyObjectResult`/`CopyPartResult` (an endpoint that ignored `x-amz-copy-source`).

  For those, Copy deletes what it made and streams the object instead (`snapstore.StreamCopy`: Open, Put, and the
  Put's digest must be the source's). Anything else fails the Copy and is not hidden behind a stream of the whole
  object: a 5xx, a 404, a network error, a 200 with an error body, or a copy that does not prove.
- **Other stores.** The disk store streams (a local copy is a read and a write of one disk). A store that has no
  server-side copy implements Copy as `snapstore.StreamCopy`.
- **A suspend's check.** `Store.Prove(key, digest)` checks an object as Verify does, but by the store's checksum
  where it keeps one. herd-api's check of a snapshot a herdlet just wrote (`takeSnapshot`: a suspend, a running
  actor's tag, a golden) is now Prove, where it was Verify.
  - In S3, one PUT's checksum must be the digest.
  - A multipart object's composite checksum must be the one Put now records with it (`X-Amz-Meta-Herd-Checksum`,
    computed in the first pass from the same bytes as the digest).
  - Prove reads the object (Verify) where the endpoint keeps no checksum, and for a composite checksum with nothing
    recorded (an object written before this change). The disk store always reads.
- **What that check gives up, said plainly.** Verify reads the bytes the endpoint serves now. Prove trusts the
  checksum the endpoint computed when it stored them. So a fault behind the endpoint after the write is no longer
  caught at the suspend: bytes rotting under an unchanged checksum, which S3 checks for itself. The herdlet's Put
  already rested on that same checksum, seconds earlier. Verify is unchanged and stays the re-read: a herdlet
  without a bundle cache still Verifies before a restore, and the bundle cache hashes what it reads.

**Why (measured).** Walked live on 2026-11-07: a setup bake's CreateTag took 16m46s and the control plane gave up at
15 minutes. The suspend spent 2m43s verifying, and CreateTag of the suspended actor about 13 minutes. Before, the
tag read the object to verify it, streamed it out and back through herd-api, and had it checked again.

Measured on this box with `TestMeasureCopy` (`HERD_MEASURE=1`), on a 512 MiB random object in 64 MiB parts, against
the in-process S3 endpoint over loopback, three runs each. The size was capped by the box's 4 GiB memory limit,
since the fake endpoint keeps objects in memory.

| What | Before | After |
|---|---|---|
| Tag of a suspended actor | 1,610,612,736 bytes through herd, 2.69 to 2.92 s | 0 bytes, 0.58 s (CopyObject) and 0.88 to 1.01 s (UploadPartCopy) |
| Check after a suspend | 536,870,912 bytes read, 0.36 s | 0 bytes, under a millisecond (one HEAD) |

The seconds after the change are the fake endpoint's own copying and hashing. Through herd, the time before grows
with the object over the link to the endpoint; after, herd-api sends only a few small requests (HEADs, and per part
a copy call), whatever the size.

**Proof here.** `snapstore/s3`:
- `TestCopyIsServerSide`: one PUT's object and a multipart one are copied with no byte through the client.
- `TestCopyPastOneCopyCopiesParts`: past the scaled CopyObject limit, which the fake enforces as S3 does, the copy is
  UploadPartCopy of the source's 11 parts.
- `TestCopyRefusesACorruptCopy`: a copy the endpoint stored corrupt is refused by its checksum with no byte read, or
  by a read without checksums, and nothing is left.
- `TestCopyWithoutChecksumsReadsTheCopy`.
- `TestCopyFallsBackToStreaming`: 501 streams, 503 fails and streams nothing.
- `TestProveReadsNothing` and `TestProveRefusesWhatTheChecksumDenies`.

`storetest` holds every store to Copy's and Prove's contract. `deploy.TestSuspendAndTagMoveNoSnapshotBytesThroughHerdAPI`
runs herd-api and a joined herdlet on the fake S3: neither the suspend nor the tag moves a snapshot byte through
herd-api.

**Not here.** No real endpoint was run: AWS, MinIO and the cluster's RustFS are untested. That covers whether each
implements CopyObject, UploadPartCopy and HEAD `?partNumber`, whether it computes a copy's checksum (rather than
carrying the source's over), and how long its copy takes. The supervisor's walk measures a tag of a built box there.

## Decisions for DEFAUL-1611 (a template's capabilities)

### A-40 A template container's capabilities change its process's set and every exec's; drop, then add

**Decision.** A template container's `security_context.capabilities` reaches the guest: herd-api checks it at
`CreateActorTemplate` and carries `add` and `drop` as written in `link.Container` (`capAdd`, `capDrop`); the herdlet
copies them into the plan's container; herd-guest builds the container's process from them (`oci.Build`,
`capabilitySets`). A name is a Linux capability (CAP_CHOWN through CAP_CHECKPOINT_RESTORE), written with or without
`CAP_` and in any case, as Kubernetes and containerd take it. `ALL` is accepted only in `drop`. Any other name is
refused at create with InvalidArgument naming the container and the name (`containers[0] (box):
security_context.capabilities.drop: capability "NET_RAWR" is not a Linux capability ...`), and nothing is stored.
The plan is checked by the same rule (`initd.Validate`), so a herdlet that is not herd-api's cannot boot one either.
The sets are:

- bounding, effective and permitted: Docker's default set (A-33), or nothing if `drop` holds ALL, plus `add`;
- inheritable and ambient: `add` alone, so a non-root USER keeps what the template added across execve (with the
  default set alone they stay empty, as before);
- `drop` applies first, then `add`, as Substrate's API defines it: a dropped default that is not added is in no set,
  and a capability named in both lists is granted in all five.

`drop: [ALL]` with `add` therefore gives exactly the added set. Every exec into the container (the exec shim that
every StartProcess runs through, and the signal helper) is started with `crun exec --process <file>`. The file is the
container's own process from its config.json (`Process.ExecProcess`): its user, environment, cwd, capabilities and
noNewPrivileges, with the exec's argv. It is written to the guest's temporary directory and removed once crun has
returned. A target with no process refuses to exec rather than leave the set to crun. A template with neither field
writes the same plan as before (no `capAdd`/`capDrop` key) and the same config.json (`testdata/config.golden.json`
unchanged).

**Why.** PLT-350's egress probe measured CapBnd 00000000a80425fb on the pool: CAP_NET_RAW was kept whatever the
template said, because only the generated pb named the field. A box's work runs through execs, not the container's
init, and `crun exec` with only an argv took the set crun fills in: crun's own fallback to config.json, which we
had never tested. The exec is now handed the process explicitly, so its set is the one tested here. The order is
Substrate's (its Capabilities message: "drop applies first, then add, so a capability in both is granted"): herd
implements the Substrate API, so a template must mean the same on herd as on Substrate. The first cut had drop win,
as containerd's CRI applies them (added, then dropped); the supervisor decided for the proto, and
`oci.TestAddIsHonouredAndAddWins` holds it. The difference shows only for a name in both lists.

An unknown name is the template's error. Refusing it at create gives the author the reason at once,
where a boot failure would surface later as a failed golden or a crashed actor.

**Counterexamples** (each seen red with its clause neutralized by hand):
`oci.TestDropNetRawHoldsItInNoSet`, `oci.TestAddIsHonouredAndAddWins`, `oci.TestUnknownCapabilityRefused`,
`oci.TestNoCapabilityFieldsNoChange`, `oci.TestExecRunsWithTheContainersCapabilities`,
`initd.TestPlanRefusesAnUnknownCapability`, `machine.TestTemplateCapabilitiesReachTheContainerAndEveryExec` (template
→ plan → herd-guest's boot → config.json and both execs), `machine.TestNoCapabilityFieldsLeaveThePlanAsBefore`, and
`conformance.TestTemplateCapabilitiesReachTheHerdlet` (create → the boot's link.Template; unknown names and add ALL
refused at create).

**Not here.** No real crun or guest kernel ran this. Nobody has yet read `/proc/self/status` CapBnd/CapEff/CapAmb
in a box and in an exec on a real host with drop NET_RAW; that read and a guest rebuild (guest/build.sh) belong to
the release walk. An exec now gets the container's environment and cwd from the process file, as runc's exec does.
The exec record's script still sets its own cwd and environment. Whether crun's argv-only exec did the same before
is unverified. `maxItems=64` on the lists is not enforced.

## Decisions for DEFAUL-1613 (a herder's unused templates are removed)

### A-41 herd lists an atespace's templates and tags, and a template's delete takes its golden unless an actor or a tag holds it

**Decision.** herd-api serves `Control.ListActorTemplates` (`apiserver/templates.go`) and `Control.ListTags`

- **By atespace.** The caller must be allowed to read in `atespace`. The proto lets an empty one list across all

  Authorizer grants per atespace. A herder lists the atespace it owns.
- **Paged by name.** Templates come in name order, `options.page_size` at a time (1 to 1000; 0 or more than 1000 is

- **As GetActorTemplate answers it.** Each template carries its `metadata` (atespace, name, uid, version,

DeleteActorTemplate already deleted the golden actor and every golden tag (and each tag's snapshot object, A-38's
names) before the record, and refused with FailedPrecondition (`template <space>/<name> is used by actor <actor>`)

FailedPrecondition (`template <space>/<name> is held by tag <tag>`) while a tag that is not one of the template's
golden names holds its uid (`status.actor_template_uid`: a tag of one of its actors). A refused delete changes

**Counterexamples** (each seen red with its clause neutralized by hand): in `conformance/templates_test.go`,

## Decisions for DEFAUL-1619 (a fork's container filesystem)

### A-42 Every herd snapshot carries each container's writable layer, and every cold boot from one puts it back

**Decision.** herd makes a tag below MEMORY hold what the issue asked for: the container's own filesystem, not only
the work volume. It does not lower what the tag reports.
- **Where the layer lives.** A container's root is its image (read-only block device) under an overlay whose upper
  directory is `/run/herd/containers/<name>/upper`, on the guest's tmpfs; the directory bound at `/tmp` is
  `/run/herd/containers/<name>/tmp`, on the same tmpfs (A-10, guest/initd). Both are guest memory. A MEMORY restore that
  runs on from the memory keeps them. Nothing else did: a bundle carried the template's volume directories only (A-19),
  so every cold boot from a bundle started the container from the bare image. That covered a VOLUMES snapshot (a
  template preferring VOLUMES or ROOTFS, or a worker that keeps no memory) and also a MEMORY bundle that cold-boots
  (a fork beside its running parent, whose link it cannot have, or a host that gives VMs no link, A-28).
- **Saved at every snapshot.** herd-guest's `Sync`, which herdlet calls before every snapshot (PLT-195), first
  archives each container's upper and `/tmp` into the share as `.herd/rootfs/<container>.tar` (package `guest/layer`;
  written beside and renamed, so a cold boot never reads half of one). The archive keeps modes, owners, times,
  symlinks, devices (an overlay whiteout is a 0/0 character device), fifos and extended attributes (an opaque
  directory's `trusted.overlay.opaque`). It leaves out sockets and the container's exec records (`/everdict/exec`):
  after a cold boot none of the processes they name runs.
- **Carried in the bundle.** herdlet writes each archive of the share's `.herd/rootfs` as `rootfs/<container>.tar`,
  after the volume tree, in every bundle (VOLUMES and MEMORY). The bundle version is 3. A restore writes the
  archives back into the new share, through os.Root; an entry that is not a plain `<name>.tar` is refused as
  ErrOutsideShare. A herdlet before this one refuses a version 3 bundle by its version (`want 1 to 2`) rather than
  restore it without the layer.
- **Restored at every cold boot.** guest/initd, before it mounts a container's overlay, extracts that container's
  archive from the share into its upper and its `/tmp` (an archive's entries cannot leave those directories: os.Root,
  and `..` refused). A share without one (a new actor, or a snapshot from a guest before this one) boots as before.
  vmm/fakeguest does the same for the containers of a VM whose memory does not hold them yet (a boot, or the restore
  of another VM's snapshot).
- **What a tag reports.** Unchanged. herd's fidelities stay VOLUMES (1) and MEMORY (3), and herd-api reports a
  snapshot at the one it took. A herd snapshot below MEMORY now holds what Substrate's ROOTFS holds: volumes plus the
  root filesystem changes since boot, put back at the cold boot. herd still reports it as VOLUMES, so it never claims
  more than it holds. A client that names it ROOTFS (everdict-herder's "rootfs") is right from this guest and
  herdlet on.

**Why.** The walk on herd v0.1.11 (2026-11-08): a parent wrote `work/walk-marker`, `/root/walk-marker` and
`/tmp/walk-marker`. everdict-herder forked it with a CreateTag of the running actor and an actor from the tag, and
reported the fork at rootfs fidelity. The fork held only `work/walk-marker`. A memory suspend and resume of the parent
kept `/root/walk-marker`, because there the memory holds the upper. Making herd hold the layer resolves the issue for
every fork, suspend and move that boots cold. Reporting VOLUMES alone would have kept a fork without the files that
an agent's tools (installed packages, `~/.cache`, `/root` dotfiles) put outside the work volume. The archive is
saved by the guest because only the guest sees the upper. The host sees the share alone, and an overlay upper on the
virtio-fs share would need virtiofsd to keep whiteouts and trusted attributes, which herd has not verified. The archive goes into every bundle, MEMORY included, because a MEMORY bundle can still cold-boot, and that is
the walk's fork.

**Cost.** Each snapshot now writes the containers' upper and `/tmp` once more, through virtio-fs into the share,
and the bundle carries those bytes. The cost scales with what the actor wrote outside its volumes since boot. A
golden snapshot's upper is small. A delegate that installs into its root filesystem pays for those bytes at every
suspend. Not measured here (no KVM in this box).

**Counterexamples** (each seen red before the fix, and with its clause neutralized by hand after it). The
conformance suite gains `fork-keeps-rootfs` (`--rootfs-path`, docs/conformance.md): a running actor writes
`/root/conformance-rootfs.txt`, a tag is taken of it while it runs, and an actor from the tag must read the file. It
was red on herd with the guest of HEAD before the fix, at VOLUMES (`TestSuiteGreenOnJoin`) and at MEMORY
(`TestSuiteGreenOnAllInOne`; the fake guest held no root for a VM id it had not run), with `file
"/root/conformance-rootfs.txt" not found`. It was red again with Sync saving no layer, with the bundle carrying none,
and with fakeguest not restoring one. `herdlet/machine.TestRootfsWritesReachForks` runs herd-guest's own boot on
both forks of a VOLUMES and a MEMORY bundle of a running parent. It is red without the save, without the bundle
entries and without initd's restore. `guest/initd.TestBootRestoresTheWritableLayerBeforeTheOverlay` (red without the
restore) checks the upper is filled before the overlay mount. `guest/agent.TestSyncSavesEachContainersLayer` (red
without the save) checks no exec records go in. `guest/layer` holds the round trip, the refusal of escaping entries
and, as root on Linux only, whiteouts and opaque directories.

**Not here.** No real host ran this: the overlay, its whiteouts and trusted attributes under a real guest kernel,
and the save's time for a large upper, are for the supervisor's walk. Hard links in an upper come back as separate
files. A MEMORY restore that runs on from the memory does not read the archive; its memory is newer.

## Decisions for DEFAUL-1622 (a restored VM's first flow)

### A-43 herd-egress holds a VM's binding before the VM can send, and re-reads a changed bindings file before it refuses an unknown address

**Decision.** A flow from a VM restored or booted a moment ago is decided under its actor's policy. It is never refused
as "bound to no actor" because herd-egress has not yet read the binding herdlet just wrote. Two clauses, each enough
on its own for a TCP flow:
- **herdlet's binding answers only once herd-egress holds it.** After each load of `-bindings`, herd-egress writes the
  bindings it now holds to `<bindings>.loaded` (`tapnet.Acknowledge`, written beside and renamed, in the bindings
  file's format). `tapnet.Bindings.Set`, which `Network.Up` runs before every Boot and Restore and `Assign` runs for a
  warm VM, waits until that file holds the binding it wrote. It waits at most `tapnet.LoadedTimeout` (10 s), then
  fails, naming herd-egress. A failed Up takes the TAP and table down, so the restore or boot fails rather than
  answer done with a VM whose flows would be refused. With no `.loaded` file, no herd-egress acknowledges (none runs
  yet, and the one that starts reads the bindings before it serves, or it predates this), and Set answers at once.
  The mechanism is a file, not a socket or a readiness endpoint. herdlet and herd-egress already share the bindings
  file's directory on every install (`/run/herd`, the all-in-one's data directory), so no new flag, port or start order
  enters the systemd, Nomad or all-in-one jobs. herd-egress watches the file by a stat every 20 ms (`bindingsPoll`);
  inotify would need a dependency herd does not vendor. A binding is therefore in force within about 20 ms of
  herdlet writing it, not at the next `-interval`.
- **A flow from an unknown address re-reads a changed file first.** `egress.Sources.OnUnknown` runs before
  `ServeTransparent` refuses an unbound source; herd-egress re-reads the bindings there if the file changed since its
  last load (a stat: herdlet renames a new file over it). The flow is refused only if the source is still unbound.
  The bound is the file's changes, not a time window. An address the file does not hold costs a stat per flow and
  causes no read, however many flows it opens, and is refused every time. A window per address would also have
  refused a VM bound just after that window's read.
- `-interval` still re-reads the file in full, as before. Removal is not acknowledged: a removed binding's VM is
  verified gone first (A-18), so it sends nothing.

**What it does not cover.** DNS does not depend on bindings. `SyntheticDNS` answers every query on `:15053`
whatever its source, so the walk's DNS queries dropped at the VM table's input chain without `ct status dnat` are a
NAT/conntrack matter, before herd-egress sees them. The WriteFile ECONNRESET right after "restore done" is the
host's call into the guest over vsock (herdlet's tunnel), which neither the TAP nor herd-egress carries. Neither has
this cause. One suspect for the DNS drop, not shown: a restored guest's resolver retries from the source port in
its memory, and a conntrack entry for that tuple left un-NATed while the address had no table would carry it past
the redirect. That needs conntrack on a failing host; it is DEFAUL-1622's remaining question.

**Why.** Real host, herd v0.1.12 (2026-11-08): a VM restored in about 200 ms began its git clone at once, and
herd-egress logged `refused / tcp 10.88.229.206:0 host-side=false: refused: connection from an address bound to no
actor`; the clone failed its TLS handshake. herdlet had written the binding (`tapnet: bound … in
/run/herd/egress-bindings.json`), and herd-egress read that file only on its 1 s ticker, so a flow in the first
second after a restore was refused. The policy itself already followed acknowledged writes (PLT-229); only the
source map lagged.

**Counterexamples** (each seen red before the fix, and with its clause neutralized by hand after it; herd-egress's
`-interval` is an hour in all of them). `deploy.TestBindingWrittenJustBeforeFirstFlowIsServed` writes a binding and
connects at once, with the watch also at an hour: red before the fix (`bound to no actor`) and with `OnUnknown` not
called. `deploy.TestHerdletBindsOnlyOnceHerdEgressHasIt` checks herd-egress holds the actor when `Bindings.Set`
answers: red before the fix, with Set not waiting, and with the watch removed (Set then times out).
`deploy.TestUnboundAddressStillRefused` (green before, a guard) is red with an unbound source served.
`deploy.TestUnknownAddressReadsOnlyAChangedFile` is red when an unknown address forces a read.
`tapnet.TestSetWaitsForHerdEgress` is red with Set not waiting.

**Not here.** No real host ran this; the walk's restore, clone and fork steps are for the supervisor.

## Decisions for DEFAUL-1626 (a release that does not change the guest rebuilds goldens)

### A-44 The guest is the same bytes from the same source, and a release that changes none of it names the same guest

**Decision.** `guest/build.sh` builds the guest (kernel and `initrd.img`, whose digests make `deploy.GuestIdentity`,
A-38) as a function of its sources alone:
- **herd-guest** (`/init`) is built `-trimpath -buildvcs=false`: no revision, commit time or dirty bit is stamped in
  it, so a commit that changes nothing it is built from leaves it the same bytes. Go's build ids are content hashes, so
  no fixed `-buildid` is needed; two builds in two clones at two paths with two empty build caches matched.
- **The initramfs** is assembled by `guest/initrd` (`go run ./guest/initrd/mkinitrd`), a Go reading of the same
  `initramfs.list` in gen_init_cpio's format, rather than by the kernel tree's gen_init_cpio, which stamps a file with
  its source's mtime and every other member with the time of the build. Every member gets `SOURCE_DATE_EPOCH` and the
  mode and owner the list gives it (root for all), members keep the list's order (a parent before its children; the
  list is checked in, so the order is fixed) and inode numbers follow it. It is compressed `gzip -9 -n`: no name or time
  in the header.
- **The kernel** is built with `KBUILD_BUILD_TIMESTAMP` (from `SOURCE_DATE_EPOCH`), `KBUILD_BUILD_USER=herd`,
  `KBUILD_BUILD_HOST=herd` and `KBUILD_BUILD_VERSION=1`.
- **`SOURCE_DATE_EPOCH`** defaults to the commit time of the last commit that touched what the guest is built from:
  `guest/`, `go.mod`, `vendor/modules.txt` and the package directories of herd-guest and mkinitrd for both
  architectures (`go list -deps`). Not the release commit's time: that would stamp every release's guest differently,
  which is the defect this fixes. A shallow clone is refused (it hides when the guest last changed); a set
  `SOURCE_DATE_EPOCH` wins.
- **The check.** `scripts/guest-repro.sh [--kernel] [rev-a [rev-b]]` builds the guest twice, in two fresh clones at two
  paths with two empty Go build caches and busybox/crun files of two different times, and fails when the artifacts
  differ; given a second revision that changes no guest source it holds the release case. `guest.TestInitrdReproducible`
  does the same from the working tree in `go test`: one revision in two checkouts, then a herdlet-only commit, must give
  the same `initrd.img`, and a commit that changes the initramfs list must not.

**Why.** Walked live on 2026-11-08: herd v0.1.13 changed herdlet and herd-egress only, and herd-api rebuilt the golden
of every template after the roll (`guest sha256:f022…`), filling a worker's four slots for minutes. herd-guest carried
the release's `vcs.revision`, and gen_init_cpio the build's time, so no two builds named the same guest.

**Counterexamples.** Before the change (with gen_init_cpio's behaviour ported as it was), `TestInitrdReproducible` and
`scripts/guest-repro.sh` are red: every member's mtime differs between two checkouts of one revision, busybox and crun
carry their download times, and `/init` differs by `vcs.revision`/`vcs.time` across a herdlet-only commit. After it,
each clause neutralized by hand is red for its own reason: without `-buildvcs=false` (`/init`'s `vcs.revision`), with
the members at the build's time (mtimes across checkouts), and with `SOURCE_DATE_EPOCH` from the release commit (mtimes
across the herdlet-only release).

**Not here.** The kernel is not built in the box (no C toolchain, no network for its clone): its reproducibility rests
on kbuild's documented variables and is compared by `scripts/guest-repro.sh --kernel` on a host that can build it.
busybox and crun are the operator's inputs; the guest is reproducible only if they are the same files (their digests
are not pinned here). The Go toolchain is an input of `/init`: a release built with another Go version is another
guest. The release tarballs themselves (`scripts/release.sh`) are not byte-reproducible; herdlet hashes the installed
kernel and initrd, not the tarball.

## Decisions for DEFAUL-1610, second round (a tag in seconds on any store)

### A-45 A tag of a suspended actor references the actor's sealed snapshot, and an object goes with the last record that names it

**Decision.** Supersedes A-39 for tags; A-39's Copy stays a `snapstore.Store` capability, and its Prove stays the
suspend's check.
- **Sealed objects.** A snapshot object is written once under a key of its own and recorded once proved (Put, then
  Prove at `takeSnapshot`). Nothing writes that key again, so a record may name an object another record names.
- **The tag references.** CreateTag of a suspended actor no longer copies. It Stats (one HEAD in S3) the actor's latest
  snapshot object and checks that the object is there with the digest the actor recorded. Then it records that same
  key and digest in the tag. No byte of the object moves, through herd-api or inside the store, whatever its size. A
  running actor's tag is unchanged: a fresh snapshot under a key of the tag's own.
- **Release by reference.** `apiserver/refs.go` `dropObject` replaces each direct delete of a snapshot object. It lists
  every actor record (its `actorState.Keys`) and every tag record (its `tagState.Snapshot`) in the record store, in
  every atespace. It deletes the object, verified gone, only when no record other than the one going names it, and
  logs that it kept one otherwise. A List that fails, or a record whose state cannot be parsed, deletes nothing: the
  tag's delete answers Unavailable and the actor's delete stays owed, so Reconcile retries it.
- **One lock.** DeleteTag and the actor delete's steps release under `refsMu`. Each holds it from its read of the
  records until the record that stops naming the object is written: the tag's delete, or the actor's delete or the
  save of what is still owed. CreateTag of a suspended actor holds it from its Stat to its record's write. So two
  holders that go at once cannot each leave the object to the other, and no tag records an object a release is
  dropping. The order is the actor's lock, then `refsMu`; nothing takes an actor's lock while holding `refsMu`.
- **Measured in the log.** `snapstore.Meter` counts the object bytes a store moves for the calls on one context: what
  an Open's reader gives (so a Verify's read), and what a Put stores, including a Put's read-back where the endpoint
  keeps no checksum. The disk and S3 stores feed it. herd-api logs every suspend's check (`actor <a>: snapshot check of
  <key>`) and every tag (`tag <t> of actor <a>: references|took snapshot <key>`) with `object_bytes`, `bytes_moved`
  and `seconds`.

**Why.** A-39's server-side copy cannot make a tag fast on MinIO with SSE-KMS: the endpoint decrypts and re-encrypts
every byte, about 3m20s for a setup bake's tag. A reference costs one HEAD on every store.

**Measured.** `TestMeasureTagOfALargeSnapshot` (`HERD_MEASURE=1`) tags a suspended actor whose object is 2 GiB on
herd-api's disk store, timed as the client sees CreateTag. Before (the copy) it took 6.615 s. After, 0.001 s, logged
with `object_bytes=2147483648 bytes_moved=0`.

**Proof here.**
- `conformance.TestTagReferencesTheSnapshot`: a 32 MiB snapshot. The tag records the actor's own key with
  `bytes_moved=0` and answers under 2 s. The object outlives its source actor's delete, a fork restores from it, and
  it goes with its last holder, tag or actor first. Both log lines carry their measurements.
- `conformance.TestFailedReferenceReadDeletesNothing`: a failing List leaves the tag's and the actor's objects, and an
  unparseable tag record leaves the tag's.
- `conformance.TestReleasesAtOnceLeaveNoObject`: two tags of one object deleted at once, with a store that holds each
  release after its read of the tags until the other has read them too. Without `refsMu` each sees the other and the
  object leaks; with it the object goes.
- `deploy.TestSuspendAndTagMoveNoSnapshotBytesThroughHerdAPI`: on the fake S3, neither the suspend nor the tag moves a
  byte through herd-api, the tag makes no CopyObject or UploadPartCopy, the bucket holds one object, and both log
  lines say `bytes_moved=0`.
- `storetest` `MeterCountsObjectBytes`: every store counts Put, Open and Verify bytes, and nothing for a Stat.

**Not here.** No real endpoint was run: the time of a HEAD on MinIO with SSE-KMS, RustFS or AWS is for the
supervisor's walk. Objects written before this change are released the same way, since each was named by one record.

## R0 spike results

Measured by the supervisor on real hosts on 2026-10-30 (Everdict knowledge entry `0ce029cf`); recorded here because
they decide R-D9. R0's repository work did not boot VMs.

- **(a) Ubuntu, Cloud Hypervisor v54.0**, i7-1165G7, Ubuntu 26.04 / kernel 7.0.0-30, 1 vCPU / 512 MiB, guest kernel
  `ch-release-v7.2.8-20261009`: boot to init 0.28 s; snapshot 0.18 s (513 MiB: config.json, memory-ranges,
  state.json); restore→resume 0.35 s, guest state continued. With virtio-fs (virtiofsd 1.13.2,
  `--migration-mode=find-paths`, shared memory) + vsock: boot 0.28 s, snapshot 0.05 s, eager restore→resume 0.07 s,
  the guest kept writing to the volume. Restore on a second host (Core Ultra 5 226V, kernel 7.0.0-38) was refused:
  "Detected incompatible CPUID entry" (leaf 0x01 ECX, leaf 0x07 EBX/ECX/EDX). Memory restore therefore needs the same
  CPU feature class — R-D9's `microvm-ch-<arch>-<cpu-class>` is **confirmed**.
- **(b) macOS 26.2, M1**, Code-Hex/vz v3, ad-hoc signed: `validateSaveRestoreSupport` = true with virtio-fs + vsock;
  boot to init 0.175–0.205 s; the share mounted. `saveMachineStateTo` fails with VZErrorDomain Code=11 "permission
  denied" from an SSH session, from `launchctl asuser`, and from a launchd agent in `gui/<uid>`, also when saving
  under /tmp. Not yet tried: a Developer ID-signed binary in an unlocked console session. R-D9's macOS row is
  **confirmed**: Macs declare VOLUMES by default; MEMORY on a Mac stays unverified.
- **(c)** One kernel source booted on both: bzImage (x86_64) under Cloud Hypervisor, Image (arm64) under VZ.

## Consequences

- Everdict talks to herd and to real Substrate through one client; methods outside the subset are not available on
  herd.
- A suspend keeps memory only where the host declared it can, and the actor resumes at MEMORY only within the
  restore family; everywhere else it resumes at VOLUMES.
- Each hypervisor backend is testable without hardware through the fake and the contract; the real backends prove
  themselves by running the same contract on a KVM host and on a Mac.
